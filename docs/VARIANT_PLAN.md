# طرح پیاده‌سازی سیستم Variable Product (برای تأیید — هیچ کدی اجرا نشده)

## ۱. نتیجهٔ بررسی کد فعلی
| بخش | وضعیت فعلی | نتیجه |
|---|---|---|
| Variant (مدل گوشی × رنگ) | `ProductVariant` با `phoneModelId`، `colorId`، یکتایی `(product, model, color)`، SKU، `isActive`، `retailPrice` (null = ارث از محصول)، `wholesalePrice`، `costPrice`، `pricingMode` | **موجود و واقعی**؛ نیازی به بازنویسی نیست |
| موجودی | `Inventory` یک‌به‌یک با Variant + `InventoryMovement` | **موجود**، در سطح Variant |
| Pricing Engine | `resolveUnitDiscount` (TS) + آینهٔ SQL، تخفیف قیمت‌گذاری، سبد/پرداخت با محاسبهٔ سرور، snapshot در `OrderItem` (قیمت اصلی، تخفیف، نام مدل/رنگ…) | **موجود**؛ فقط روی آن سوار می‌شویم |
| Bulk قیمت | API و صفحهٔ `/admin/pricing` (درصدی/مبلغ ثابت/قیمت مستقیم، پیش‌نمایش، تاریخچه) | **موجود**، باید به Matrix وصل شود |
| Multi-Category / Brand | همین امروز انجام شد: دسته/برند اصلی + نامحدود اضافی (`ProductCategory`/`ProductBrand`) | **انجام شده** (معادل M2M با اصلی برای Breadcrumb/SEO) |
| دموی Matrix و مدل‌ها | فقط UI با داده ساختگی | باید به API واقعی وصل شود |
| Series | وجود ندارد | **جدید** |
| تصویر اختصاصی Variant | وجود ندارد (`ProductImage` فقط سطح محصول) | **جدید** |
| قیمت فروش ویژه Variant | وجود ندارد (تخفیف فقط سطح محصول/Discount) | **جدید** |
| Attributeهای عمومی (جنس، طرح، …) | وجود ندارد | **جدید** (توصیفی) |
| Generator ترکیب‌ها | فقط در دمو | **جدید** |

## ۲. تغییرات دیتابیس (همه افزایشی، بدون حذف/تغییر ستون‌های موجود، یک Migration جدید)
1. `PhoneSeries { id, brandId→Brand, name, slug(unique), sortOrder, isActive }` و `PhoneModel.seriesId String?` (nullable؛ مدل‌های فعلی بدون Series می‌مانند، ادمین بعداً گروه‌بندی می‌کند؛ اسکریپت اختیاری برای حدس Series از نام مثل «iPhone 13 Pro» → «iPhone 13»، فقط با تأیید شما).
2. `ProductVariant.salePrice Int?` (قیمت فروش ویژه، null = ندارد) و `ProductVariant.imageId String?` → `ProductImage` (SetNull). تصویر اختصاصی از همان گالری/آپلود موجود انتخاب می‌شود.
3. Attributeهای عمومی: `Attribute { name, slug, type, sortOrder, isActive }`، `AttributeValue { attributeId, value, hex? }`، `ProductAttributeValue { productId, valueId }` — توصیفی و قابل انتخاب در فرم و قابل نمایش در مشخصات صفحه محصول. برای آینده `Attribute.usedForVariants Boolean @default(false)` و جدول `VariantAttributeValue { variantId, valueId }` **فقط رزرو می‌شود** (در این فاز ساخته نمی‌شود تا آینده بدون بازنویسی ممکن باشد).
4. هیچ داده‌ای حذف/بازنویسی نمی‌شود؛ قبل از اجرا روی سرور طبق روال قبل بک‌آپ (`backup.sh`) و بررسی زنجیرهٔ Migration روی دیتابیس خالی انجام می‌شود.

## ۳. منطق قیمت (سوار بر موتور فعلی)
`قیمت پایهٔ محصول → override قیمت Variant (یا ارث) → بهترین تخفیف واحد (legacy + Discount + salePrice Variant) → قیمت نهایی`
- `salePrice` به‌عنوان یک کاندیدای تخفیف در `resolveUnitDiscount` و آینهٔ SQL (`effective-sql.ts`) اضافه می‌شود؛ قانون «بهترین تخفیف تکی» بدون تغییر.
- همچنان فقط سرور قیمت را حساب می‌کند؛ سبد و پرداخت دوباره محاسبه می‌کنند؛ snapshot سفارش همان فیلدهای موجود است و تغییر بعدی قیمت Variant روی سفارش قبلی اثر ندارد (تست می‌شود).
- Variant غیرفعال یا موجودی صفر: در صفحه مشتری قابل انتخاب نیست، در API سبد رد می‌شود (بررسی سرور، نه فقط UI).

## ۴. API (ادمین، با `adminRoute` و مجوزهای فعلی + CSRF + audit)
- `GET /api/admin/products/:id/variants` (جستجو/فیلتر مدل، رنگ، برند، Series، وضعیت، موجودی، صفحه‌بندی)
- `POST …/variants/generate` (ورودی: مدل‌ها × رنگ‌ها؛ خروجی پیش‌نمایش؛ ساخت ترکیب‌ها با **وضعیت پیش‌فرض غیرفعال** مگر ادمین فعال کند، SKU خودکار قابل ویرایش، ترکیب تکراری ساخته نمی‌شود؛ سقف مثلاً ۳۰۰ ترکیب در هر درخواست)
- `PATCH …/variants/:vid` (SKU، قیمت/ارث، salePrice، موجودی با ثبت حرکت، فعال، تصویر)
- `POST …/variants/bulk` (انتخاب‌شده‌ها: فعال/غیرفعال، موجودی، و عملیات قیمت: +/− ثابت، +/− درصد، تعیین قیمت، حذف override) — از موتور bulk فعلی استفاده می‌کند، با پیش‌نمایش و تاریخچه قیمت
- CRUD `series` و `attributes` از طریق رجیستری `resources.ts`

## ۵. رابط ادمین (همان دمو، به داده واقعی وصل می‌شود)
- تب/بخش Variant در فرم محصول = Matrix دمو با ستون‌های مدل، رنگ، SKU، قیمت، قیمت ویژه، موجودی، وضعیت ✓/×، تصویر؛ جستجو، فیلتر، انتخاب گروهی، عملیات گروهی، ویرایش.
- مدیریت مدل گوشی: افزودن Series (برند → Series → مدل).
- مدیریت Attributeها (صفحهٔ جدید، همان سبک صفحات فعلی) و انتخاب آن‌ها در فرم محصول.
- بدون تغییر در رنگ/فونت/Header/Footer/کارت‌ها/طرح صفحه محصول؛ فقط اجزای لازم در همان Design System.

## ۶. صفحه مشتری
- انتخاب مدل به‌صورت Chip (همان دمو) با جستجو، گروه‌بندی برند، فیلتر Series؛ انتخاب مدل+رنگ → یافتن Variant معتبر؛ ترکیب ناموجود/غیرفعال/ناموجودی = disabled واضح.
- تصویر Variant هنگام انتخاب، در گالری جایگزین می‌شود؛ بدون تصویر = تصویر اصلی محصول.
- فقط داده‌ای که سرور می‌دهد استفاده می‌شود؛ بودجهٔ اندازهٔ صفحه/تعداد کوئری (تست‌های فعلی) حفظ می‌شود (برای مدل‌های زیاد، لیست Chip با جستجو سمت کلاینت روی همان payload کم‌حجم).

## ۷. تست و تحویل
تست e2e جدید: generate (۴۰ ترکیب، پیش‌فرض غیرفعال)، فعال/غیرفعال، رد سبد برای غیرفعال/ناموجود، ارث/override/salePrice در کارت و سبد و پرداخت، snapshot سفارش، bulk (۶ عملیات)، تصویر Variant، Series، مجوزها؛ به‌علاوه تست مرورگر برای انتخاب مدل/رنگ. سپس کل e2e/browser/lint/tsc/build، Migration روی دیتابیس خالی، و فایل نهایی + دستور پاورشل. اجرای Migration روی سرور فقط با `update.sh` و بک‌آپ قبلی؛ من مستقیماً روی Production کاری نمی‌کنم.

## ۸. ریسک‌ها / نکات تصمیم‌گیری
- Series برای مدل‌های فعلی خالی می‌ماند تا شما گروه‌بندی کنید (یا تأیید اسکریپت حدس خودکار).
- Attributeهای عمومی در این فاز توصیفی‌اند؛ تبدیل به Variant واقعی بعداً با جدول رزروشده، بدون بازنویسی.
- «قیمت فروش ویژه» را به‌صورت «قیمت نهایی فروش Variant» تعریف می‌کنم (تخفیف = قیمت − salePrice) و با تخفیف‌های دیگر به قاعدهٔ بهترین تخفیف تکی تابع است.
