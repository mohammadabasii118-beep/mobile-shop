# برنامه مهاجرت: نقش SUPER_ADMIN و جدول‌های مدیریت طراحی

وضعیت: **پیشنهادی، منتظر تأیید**. تا زمان تأیید هیچ چیز روی دیتابیس اصلی اجرا نشده و `prisma/schema.prisma` هم تغییر نکرده است.

فایل‌های همراه این سند:

| فایل | کاربرد |
|---|---|
| `schema.additions.prisma` | مدل‌های پیشنهادی (پیش‌نویس) |
| `001_super_admin_and_design_tables.sql` | SQL مهاجرت؛ با `prisma migrate diff` ساخته شده |
| `001_rollback.sql` | بازگشت کامل |

## ۱. بررسی ساختار فعلی نقش‌ها

- enum `Role`: `CUSTOMER`، `ADMIN`، `STAFF`.
- `User.permissions` (آرایه‌ی رشته) فقط برای `STAFF` است و تنها مقدار مؤثرش `SUPPORT` است.
- نقش داخل JWT نشست (next-auth) ذخیره می‌شود و تا پایان اعتبار توکن از دیتابیس دوباره خوانده نمی‌شود.
- `SupportMessage.senderRole` هم از همین enum استفاده می‌کند. در تست بازگشت همین مورد باعث خطا شد و در `001_rollback.sql` رفع شد.
- گاردها:
  - `requireAdmin()` در ۵۴ نقطه استفاده شده و فقط `role === "ADMIN"` را می‌پذیرد.
  - `requireStaffPermission()` و `requireAdminOrStaff()`.
- جاهایی که نقش با رشته‌ی `"ADMIN"` مقایسه می‌شود:
  `lib/actions/guard.ts`، `middleware.ts`، `app/admin/(protected)/layout.tsx`، `app/admin/login/page.tsx`، `app/api/receipts/[filename]/route.ts`، `app/checkout/card-transfer/[orderId]/page.tsx`، `lib/actions/cardTransfer.ts`.
- `prisma/seed.ts` یک ادمین با رمز ثابت `Admin@12345` می‌سازد.
- پروژه پوشه‌ی `prisma/migrations` ندارد و با `db push` کار کرده است.

## ۲. طراحی نقش SUPER_ADMIN

قواعد:

1. `SUPER_ADMIN` فقط به enum اضافه می‌شود (`ALTER TYPE "Role" ADD VALUE`). این کار داده‌ای را عوض نمی‌کند.
2. ادمین‌های فعلی خودکار ارتقا پیدا **نمی‌کنند** و `ADMIN` می‌مانند.
3. `SUPER_ADMIN` همه‌ی توانایی‌های `ADMIN` را دارد. برای این کار یک تابع مشترک در `lib/roles.ts` (`isAdminRole`) می‌سازم و هفت نقطه‌ی بالا را به آن تغییر می‌دهم. اگر این کار انجام نشود مدیر اصلی از سفارش‌ها و رسیدها بیرون می‌ماند.
4. فقط `SUPER_ADMIN` به این موارد دسترسی دارد: بنرها، موشن‌گرافیک، صفحه‌ساز، لوگو و رنگ‌ها، تنظیمات انیمیشن.
5. گارد جدید `requireSuperAdmin()`:
   - نقش را **از دیتابیس** می‌خواند، نه فقط از JWT. اگر نقش کسی پایین آورده شود، فوراً اثر می‌کند.
   - اگر `REQUIRE_SUPER_ADMIN_2FA=true` باشد، حساب باید ورود دومرحله‌ای فعال داشته باشد. (پیشنهاد: فعال باشد.)
   - همه‌ی Server Actionها و APIهای طراحی این گارد را اول کار صدا می‌زنند.
6. مسیرهای `/admin/design/*` در `middleware`/`proxy` فقط برای `SUPER_ADMIN` باز است. این فقط لایه‌ی اول است و اصل کنترل در Server Actionهاست.
7. `ADMIN` و `STAFF` نمی‌توانند حساب `SUPER_ADMIN` را ویرایش یا حذف کنند. (اکنون هیچ اکشنی نقش کاربران را تغییر نمی‌دهد و این قاعده فقط برای آینده تثبیت می‌شود.)
8. هیچ صفحه‌ای در رابط کاربری برای ساخت `SUPER_ADMIN` نمی‌سازم.

### اسکریپت ساخت مدیر اصلی (`scripts/createSuperAdmin.ts`)

- تعاملی است و از terminal می‌پرسد: ایمیل، نام، رمز (بدون نمایش روی صفحه) و تکرار رمز.
- ایمیل و رمز هیچ‌جا در کد، `.env` یا لاگ ذخیره نمی‌شود.
- شرایط رمز: حداقل ۱۲ نویسنده، رد کردن رمزهای رایج، bcrypt با cost ۱۲.
- اگر ایمیل قبلاً وجود داشته باشد فقط با تایپ عبارت تأیید ارتقا می‌دهد و رمز را تغییر نمی‌دهد.
- بعد از ساخت یادآوری می‌کند که ورود دومرحله‌ای را از `/admin/security` فعال کنید.
- در `prisma/seed.ts` بلوک ادمین با رمز ثابت **حذف** می‌شود.

## ۳. جدول‌های جدید (فقط افزودنی)

هیچ جدول یا ستون موجودی تغییر نمی‌کند. جدول‌های سفارش، محصول، پرداخت، کیف پول و کاربر دست‌نخورده می‌مانند. تنها تغییر روی چیزی که از قبل هست، افزودن یک مقدار به enum `Role` است.

| جدول | کاربرد |
|---|---|
| `MediaAsset` | تصویر، ویدئو (MP4/WebM) و انیمیشن آپلودشده؛ نوع، حجم، ابعاد، متن جایگزین |
| `DesignBanner` | بنرهای Hero، تبلیغاتی و کمپین با تصویر جدا برای موبایل/دسکتاپ، متن و لینک دکمه‌ها، ترتیب، فعال/غیرفعال، زمان شروع/پایان، وضعیت پیش‌نویس/منتشرشده |
| `MotionSetting` | تنظیم هر موشن‌گرافیک با کلید: حالت (خاموش/CSS/سه‌بعدی/ویدئو/انیمیشن)، فعال بودن، فایل، تصویر جایگزین، پارامترهای معتبرسنجی‌شده |
| `ThemeSettings` | لوگوی روشن/تیره، فاویکون، رنگ‌های برند، متن‌های معرفی |
| `PageLayout` | نسخه‌های صفحه‌ی اصلی برای صفحه‌ساز؛ هر نسخه فهرستی از بلوک‌های مجاز |
| `DesignAuditLog` | ثبت اینکه چه کسی، چه چیزی را، چه زمانی تغییر داد |

نکته‌ها:

- جدول `Banner` و `HomepageSection` فعلی حذف نمی‌شوند. تا وقتی `PageLayout` منتشرشده وجود نداشته باشد، صفحه‌ی اصلی همان‌ها را مثل قبل نشان می‌دهد. در نتیجه سایت بعد از مهاجرت و پیش از هر تنظیمی، بدون تغییر کار می‌کند.
- بنر فعلی (یک ردیف) در یک مرحله‌ی جداگانه و **کپی** می‌شود، نه انتقال.
- `PageLayout.blocks` فقط از نوع‌های ثابت (`HERO`، `CATEGORY_STRIP`، `PRODUCT_RAIL`، `PROMO_BANNERS`، `BENEFITS`، `BRAND_FILM`، `ABOUT`، `CUSTOM_BLOCK`) و با اعتبارسنجی zod ساخته می‌شود. هیچ HTML یا کد آزاد پذیرفته نمی‌شود.
- انتشار = تغییر وضعیت یک نسخه به `PUBLISHED`. بازگشت به نسخه‌ی قبلی = انتشار دوباره‌ی نسخه‌ی قدیمی.

## ۴. آپلود فایل‌ها

- مسیر دائمی جدا: `public/uploads/design/` (در `.gitignore` و در اسکریپت `backup.sh` هست).
- تشخیص نوع از روی بایت‌ها (تصویر: jpeg/png/webp/gif/avif؛ ویدئو: MP4 و WebM). پسوند و `file.type` مرورگر معتبر نیستند.
- SVG آپلودی مجاز نیست (خطر اسکریپت).
- سقف حجم: تصویر ۵ مگابایت، ویدئو ۲۰ مگابایت (قابل تنظیم با env).
- نام فایل تصادفی سمت سرور، بدون استفاده از نام اصلی.
- Server Action آپلود با `requireSuperAdmin()`. آپلود فعلی محصولات که `requireAdmin` است بدون تغییر می‌ماند.
- سایز بدنه‌ی Server Action الان ۱۰ مگابایت است. برای ویدئو یا آپلود مستقیم جداگانه (Route Handler) یا افزایش سقف لازم است. پیشنهاد من Route Handler است.
- CSP در `next.config.mjs` برای ویدئو (`media-src 'self'`) و Three.js (`worker-src blob:`) اصلاح می‌شود.

## ۵. روش اجرای مهاجرت (بعد از تأیید شما)

1. **بکاپ کامل**: `npm run backup` (دیتابیس + پوشه‌ی آپلود). نسخه را خارج از سرور هم نگه دارید.
2. **تعیین baseline**: چون پروژه با `db push` ساخته شده، ابتدا وضعیت فعلی دیتابیس را به‌عنوان مهاجرت پایه ثبت می‌کنم:
   `prisma migrate diff` برای ساخت `0_init` و `prisma migrate resolve --applied 0_init`. این مرحله چیزی روی داده‌ها اجرا نمی‌کند.
3. **تست روی کپی**: دیتابیس را به یک کپی بازیابی می‌کنید و `001_...sql` را با `psql -1` (یک تراکنش) روی آن اجرا می‌کنید.
4. **اجرای واقعی** با `prisma migrate deploy`، در پنجره‌ی کم‌ترافیک.
5. ساخت مدیر اصلی: `npx tsx scripts/createSuperAdmin.ts`.
6. راه‌اندازی مجدد برنامه (`pm2 restart`) و اجرای چک‌لیست تست.

نتیجه‌ی تست انجام‌شده روی دیتابیس آزمایشی **خودم** (نه دیتابیس شما): SQL بدون خطا اجرا شد، `Role` چهار مقدار پیدا کرد و شش جدول ساخته شد. بازگشت هم اجرا شد و بعد از آن اجرای دوباره‌ی مهاجرت هم موفق بود.

## ۶. روش بازگشت

| سطح | کار |
|---|---|
| کد | برگشت به تگ/پوشه‌ی نسخه‌ی قبلی، `npm ci && npm run build`، راه‌اندازی مجدد. جدول‌های جدید روی نسخه‌ی قبلی کد بی‌اثرند. |
| دیتابیس (سبک) | `psql -1 -f docs/migration/001_rollback.sql` (فقط محتوای طراحی حذف می‌شود؛ سفارش‌ها و کاربران دست نمی‌خورند) |
| دیتابیس (کامل) | `npm run restore` از بکاپ مرحله‌ی ۱ |

نکته: PostgreSQL نمی‌تواند یک مقدار enum را حذف کند. اسکریپت بازگشت enum `Role` را دوباره می‌سازد. اگر بازگشت لازم نیست، وجود مقدار اضافه‌ی `SUPER_ADMIN` بی‌ضرر است.

## ۷. تست‌های دسترسی و نشست (پیش از تحویل)

بعد از تبدیل `middleware.ts` به `proxy.ts` این ماتریس را روی سرور واقعی Next اجرا می‌کنم:

| کاربر | `/admin` | `/admin/design/*` | Server Action طراحی (مستقیم) | `/api` طراحی |
|---|---|---|---|---|
| ناشناس | رد | رد | رد | ۴۰۱ |
| مشتری | رد | رد | رد | ۴۰۳ |
| STAFF بدون مجوز | رد | رد | رد | ۴۰۳ |
| STAFF با SUPPORT | فقط پشتیبانی | رد | رد | ۴۰۳ |
| ADMIN | مجاز | **رد** | **رد** | ۴۰۳ |
| SUPER_ADMIN | مجاز | مجاز | مجاز | مجاز |

تست‌های نشست:

- توکن قدیمی بعد از پایین آمدن نقش (گارد DB اثر بگذارد).
- خروج از حساب و ورود مجدد.
- ورود دومرحله‌ای، کد پشتیبان، محدودیت تلاش ورود (`LoginAttempt`).
- دست‌کاری کوکی نشست.

## ۸. رفع مشکل به‌روزرسانی صفحات استاتیک

صفحه‌هایی مثل `/cart` و `/about` هنگام Build با تنظیمات سایت ساخته می‌شوند و بعد از ذخیره در پنل تغییر نمی‌کنند. راه‌حل: `getSiteSettings`/`ThemeSettings` را با برچسب کش (`cacheTag`) بخوانم و هر Server Action ذخیره‌ی تنظیمات `revalidateTag` و `revalidatePath("/", "layout")` صدا بزند. تست: تغییر عنوان از پنل و دیدن آن در `/cart` بدون Build مجدد.
