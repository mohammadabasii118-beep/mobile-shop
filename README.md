# کیس لاین — فروشگاه اینترنتی Production-Ready

پروژه‌ای کامل و واقعی روی **Next.js 14 (App Router) + TypeScript + Prisma + PostgreSQL + NextAuth + Tailwind**، شامل فروشگاه کامل، پنل مدیریت در `/admin`، موتور قیمت‌گذاری، درگاه پرداخت (زرین‌پال به‌صورت پیش‌فرض و قابل تعویض)، و اسکلت آماده برای اتصال API تأمین‌کننده.

> این یک Demo نیست. تمام صفحات به دیتابیس واقعی وصل‌اند و عملیات CRUD واقعی انجام می‌دهند.

---

## ۱. اجرای پروژه (Local)

### پیش‌نیازها
- Node.js نسخه ۱۸ یا بالاتر
- PostgreSQL (لوکال، Docker، یا یک سرویس ابری مثل Neon/Supabase/Railway)

### مراحل
```bash
# ۱. نصب وابستگی‌ها
npm install

# ۲. کپی فایل نمونه محیطی و ویرایش مقادیر
cp .env.example .env
# سپس مقدار DATABASE_URL و NEXTAUTH_SECRET را در .env تنظیم کنید

# ۳. ساخت جداول دیتابیس
npm run db:push

# ۴. وارد کردن داده‌های نمونه (دسته‌بندی‌ها، چند محصول، کاربر ادمین، کدهای تخفیف، قوانین قیمت‌گذاری)
npm run db:seed

# ۵. اجرای پروژه در حالت توسعه
npm run dev
```

سپس به آدرس زیر بروید:
- فروشگاه: `http://localhost:3000`
- پنل مدیریت: `http://localhost:3000/admin/login`

**اطلاعات ورود پیش‌فرض ادمین** (ساخته‌شده توسط seed):
```
ایمیل: admin@caseline.ir
رمز عبور: Admin@12345
```
⚠️ حتماً بلافاصله پس از اولین ورود این رمز را از دیتابیس (یا با ساخت یک صفحه تغییر رمز) عوض کنید.

اگر می‌خواهید دیتابیس را با Prisma Studio ببینید:
```bash
npm run db:studio
```

## ۳. محل تنظیم دیتابیس، درگاه پرداخت و API تأمین‌کننده

همه‌چیز از طریق **Environment Variables** در فایل `.env` کنترل می‌شود؛ هیچ Secret‌ای در کد Frontend قرار ندارد.

| بخش | کجا تنظیم می‌شود |
|---|---|
| دیتابیس | متغیر `DATABASE_URL` در `.env` |
| درگاه پرداخت (زرین‌پال) | متغیرهای `ZARINPAL_*` در `.env`؛ پیاده‌سازی در `lib/payment/zarinpal.ts` |
| تعویض درگاه پرداخت | یک فایل جدید مثل `lib/payment/idpay.ts` با همان اینترفیس `PaymentProvider` بسازید و در `lib/payment/index.ts` فقط خط `export const paymentProvider = ...` را عوض کنید — هیچ‌جای دیگر کد نیاز به تغییر ندارد |
| API تأمین‌کننده | متغیرهای `SUPPLIER_API_URL` و `SUPPLIER_API_KEY` در `.env`؛ پیاده‌سازی واقعی را در `lib/supplier/index.ts` (به‌جای `NotConfiguredSupplierClient`) اضافه کنید. جریان Sync در `scripts/syncSupplier.ts` آماده است و از موتور قیمت‌گذاری (`lib/pricing.ts`) به‌طور خودکار استفاده می‌کند |
| قوانین قیمت‌گذاری | از پنل مدیریت → «قوانین قیمت‌گذاری» (جدول `PricingRule` در دیتابیس) |
| بنر و بخش‌های صفحه اصلی | از پنل مدیریت → «صفحه اصلی» |

## ۴. تمام Environment Variableها

فایل `.env.example` را به `.env` کپی و مقداردهی کنید:

```env
# دیتابیس PostgreSQL
DATABASE_URL="postgresql://user:pass@host:5432/dbname?schema=public"

# NextAuth — این مقدار را حتماً تصادفی و طولانی تنظیم کنید:
# openssl rand -base64 32
NEXTAUTH_SECRET="..."
NEXTAUTH_URL="https://yourdomain.com"       # در local: http://localhost:3000

# آدرس عمومی سایت (برای Metadata، Sitemap، Callback پرداخت)
NEXT_PUBLIC_SITE_URL="https://yourdomain.com"
NEXT_PUBLIC_SITE_NAME="کیس لاین"

# درگاه پرداخت زرین‌پال
ZARINPAL_MERCHANT_ID="..."                   # از پنل زرین‌پال
ZARINPAL_SANDBOX="true"                      # false در Production
ZARINPAL_CALLBACK_URL="https://yourdomain.com/api/payment/callback"

# API تأمین‌کننده (فعلاً خالی — بعداً تکمیل می‌شود)
SUPPLIER_API_URL=""
SUPPLIER_API_KEY=""
```

## ۵. Deploy روی هاست (Production)

پروژه یک اپلیکیشن استاندارد Next.js است و روی هر هاستی که از Node.js یا Docker پشتیبانی کند قابل اجراست. دو مسیر رایج:

### گزینه الف) Vercel + دیتابیس مدیریت‌شده (ساده‌ترین مسیر)
1. پروژه را در یک ریپازیتوری Git (GitHub/GitLab) قرار دهید.
2. یک دیتابیس PostgreSQL بسازید — مثلاً [Neon](https://neon.tech) یا [Supabase](https://supabase.com) (رایگان برای شروع).
3. پروژه را در [Vercel](https://vercel.com) وارد (Import) کنید.
4. تمام Environment Variableهای بخش ۴ را در تنظیمات پروژه‌ی Vercel وارد کنید.
5. در تنظیمات Build، دستور `npm run db:push && npm run db:seed` را فقط برای اولین بار (یک‌بار) دستی از طریق `vercel env pull` + اجرای لوکال یا از طریق یک Job جدا اجرا کنید (Seed را روی هر Deploy اجرا نکنید).
6. Deploy کنید.

### گزینه ب) VPS / سرور اختصاصی (Docker یا PM2)
1. Node.js ۱۸+ و PostgreSQL را روی سرور نصب کنید (یا از Docker Compose برای Postgres استفاده کنید).
2. کد را روی سرور Clone/Upload کنید.
3. `.env` را با مقادیر Production تنظیم کنید (دامنه واقعی، NEXTAUTH_SECRET جدید، اطلاعات زرین‌پال واقعی).
4. اجرا:
   ```bash
   npm install
   npm run build
   npm run db:push
   npm run db:seed   # فقط بار اول
   npm run start     # یا با pm2: pm2 start npm --name caseline -- start
   ```
5. با Nginx یا Caddy به‌عنوان Reverse Proxy، دامنه را به پورت ۳۰۰۰ وصل و SSL (Let's Encrypt) فعال کنید.

میزبان‌های ایرانی مثل **لیارا (Liara)** هم از Next.js و PostgreSQL مدیریت‌شده پشتیبانی می‌کنند و مراحل مشابه گزینه (الف) است.

## ۶. نکات امنیتی که رعایت شده

- رمزهای عبور با **bcrypt** هش می‌شوند؛ هیچ‌جا متن ساده ذخیره نمی‌شود.
- `/admin/*` و `/account/*` با `middleware.ts` و بررسی مجدد نقش کاربر در Layout سرور محافظت می‌شوند.
- تمام ورودی‌های فرم (ثبت‌نام، ورود، Checkout، پیام تماس، فرم‌های ادمین) با **Zod** اعتبارسنجی می‌شوند.
- قیمت نهایی سفارش همیشه **سمت سرور و از دیتابیس** محاسبه می‌شود، نه از مقدار ارسالی مرورگر — از دستکاری قیمت در Checkout جلوگیری می‌کند.
- هیچ Secret (کلید درگاه، اتصال دیتابیس) در کد Frontend/کلاینت قرار ندارد؛ همه از طریق Environment Variables سمت سرور خوانده می‌شوند.
- Session با JWT امن (NextAuth) مدیریت می‌شود.

## ۹. پرداخت کارت‌به‌کارت (اضافه‌شده)

در کنار زرین‌پال، مشتری می‌تواند «کارت‌به‌کارت» را در تسویه‌حساب انتخاب کند، شماره کارت/بانک را ببیند (با دکمه کپی)، و تصویر رسید + شماره پیگیری (اختیاری) را آپلود کند. سفارش تا تأیید دستی شما در `PENDING_PAYMENT` می‌ماند.

- **تنظیم شماره کارت/بانک:** از پنل → «تنظیمات کارت بانکی» (`/admin/settings`) — بدون نیاز به ویرایش کد.
- **بررسی و تأیید/رد رسیدها:** از پنل → «پرداخت‌های کارت‌به‌کارت» (`/admin/card-transfers`) یا مستقیم از صفحه جزئیات همان سفارش. تأیید، وضعیت سفارش را به «پرداخت‌شده» تغییر می‌دهد؛ رد، دلیل را ثبت می‌کند و مشتری می‌تواند رسید جدید بفرستد.
- **امنیت رسیدها:** فایل‌های رسید در `private-uploads/receipts/` (خارج از پوشه عمومی `public/`) ذخیره می‌شوند و فقط از مسیر احرازهویت‌شده `app/api/receipts/[filename]` قابل مشاهده‌اند — فقط صاحب سفارش (در صورت داشتن حساب) یا مدیر. حداکثر حجم فایل ۵ مگابایت و فقط فرمت‌های تصویری مجازند.
- **تغییرات دیتابیس:** دو مدل جدید (`CardTransferReceipt`, `BankCardSettings`) و یک فیلد جدید روی `Order` (`paymentMethod`, پیش‌فرض `ZARINPAL`) اضافه شده — کاملاً افزایشی است و هیچ داده‌ی قبلی (محصولات، کاربران، سفارش‌ها) را تغییر یا حذف نمی‌کند. بعد از گرفتن کد جدید، فقط یک بار روی سرور اجرا کنید:
  ```bash
  npx prisma generate
  npm run db:push
  ```
- **مجوز نوشتن:** پروسه Node باید علاوه بر `public/uploads`، به پوشه‌ی جدید `private-uploads/` هم دسترسی نوشتن داشته باشد (به‌صورت خودکار در اولین آپلود ساخته می‌شود).

## ۱۰. اصلاحات امنیتی کارت‌به‌کارت + محصولات متغیر (آخرین به‌روزرسانی)

### ۱۰.۱ مهاجرت امن دیتابیس

همه‌ی تغییرات این نسخه **افزایشی (Additive)** هستند؛ هیچ جدول یا فیلد قبلی حذف یا بازنویسی نشده و داده‌های موجود (محصولات، کاربران، سفارش‌ها، رسیدها) دست‌نخورده می‌مانند. مدل‌های جدید: `Color`, `ProductVariant`. فیلدهای جدید: `Order.guestToken`, `Product.hasVariants`, `OrderItem.variantId`, `OrderItem.variantLabel`, `PhoneModel.brandId`.

روی سرور Production، **قبل از هر چیز از دیتابیس Backup بگیرید**، سپس:

```bash
npm install
npx prisma generate
npm run db:push      # یا: npx prisma migrate deploy در صورت استفاده از Migration فایل‌دار
```

فیلد `Order.guestToken` عمداً Nullable تعریف شده تا سفارش‌های قدیمی (قبل از این آپدیت) بدون توکن هم مشکلی نداشته باشند؛ فقط سفارش‌های جدید از این پس توکن می‌گیرند. نیازی به هیچ اسکریپت مهاجرت دستی داده نیست.

اختیاری: `npm run db:seed` را دوباره اجرا کنید تا رنگ‌ها، مدل‌های وابسته به برند، و دو محصول متغیر نمونه («قاب سیلیکونی» و «گلس محافظ») برای تست اضافه شوند — این کار idempotent است و محصولات/کاربران موجود را تغییر نمی‌دهد.

### ۱۰.۲ امنیت کارت‌به‌کارت (سفارش‌های مهمان)

- هر سفارش هنگام ثبت یک **توکن تصادفی و غیرقابل‌حدس** (۲۴ بایت، base64url) می‌گیرد (`Order.guestToken`). برای سفارش‌های مهمان (بدون حساب کاربری)، این توکن — نه شناسه سفارش — کلید دسترسی به صفحه‌ی پرداخت کارت‌به‌کارت و تصاویر رسید است؛ توکن در URL به‌صورت `?t=...` منتقل می‌شود (لینک «ارسال رسید» در پیگیری سفارش و ریدایرکت بعد از ثبت سفارش هر دو آن را می‌سازند).
- تصاویر رسید در `private-uploads/receipts/` (خارج از `public/`) ذخیره و فقط از طریق `app/api/receipts/[filename]` سرو می‌شوند؛ این مسیر برای هر درخواست، مالکیت سفارش (حساب کاربری یا توکن مهمان) یا نقش ADMIN را دوباره بررسی می‌کند.
- نوع واقعی فایل آپلودی با بررسی Magic Bytes (نه فقط پسوند یا MIME مرورگر) در `lib/fileValidation.ts` تأیید می‌شود؛ حداکثر حجم ۵ مگابایت.
- ارسال رسید محدود به ۵ بار در هر سفارش و حداقل ۳۰ ثانیه فاصله بین ارسال‌هاست (`lib/actions/cardTransfer.ts`).
- فقط کاربر با نقش `ADMIN` می‌تواند رسید را تأیید/رد کند (`requireAdmin()`).
- تأیید/رد رسید داخل یک **تراکنش دیتابیس** با الگوی «Claim» (`updateMany` با شرط `status: PENDING`) انجام می‌شود تا دو درخواست هم‌زمان هرگز هر دو موفق نشوند؛ تغییر وضعیت سفارش به «پرداخت‌شده» هم در همان تراکنش انجام می‌شود.
- آپلود رسید **هرگز** وضعیت سفارش را تغییر نمی‌دهد؛ فقط تأیید دستی مدیر این کار را انجام می‌دهد.

### ۱۰.۳ محصولات متغیر

- در فرم افزودن/ویرایش محصول، تیک «این محصول متغیر است» را بزنید و محصول را ذخیره کنید، سپس از دکمه‌ی «مدیریت متغیرها» ترکیب‌های برند/مدل/رنگ را با قیمت، موجودی، تصویر و SKU جداگانه تعریف کنید.
- برندها، مدل‌های گوشی (وابسته به برند) و رنگ‌ها از پنل → «برندهای گوشی» / «مدل‌های گوشی» / «رنگ‌ها» مدیریت می‌شوند.
- هر بُعد (برند/مدل/رنگ) اختیاری است؛ مثلاً برای گلس محافظ فقط برند+مدل کافی است و رنگی تعریف نمی‌شود — در صفحه محصول فقط ابعادی که واقعاً برایشان داده ثبت شده نمایش داده می‌شوند.
- در صفحه محصول، مشتری برند → مدل → رنگ را انتخاب می‌کند و قیمت/موجودی/تصویر همان ترکیب نمایش داده می‌شود؛ ترکیب‌های ناموجود یا غیرفعال قابل افزودن به سبد نیستند (هم در رابط کاربری و هم دوباره در سرور هنگام ثبت سفارش بررسی می‌شود).
- انتخاب دقیق مشتری (`OrderItem.variantId` + یک متن خلاصه مثل «Apple / iPhone 14 / صورتی» در `OrderItem.variantLabel`) در سبد خرید، سفارش، فاکتور و پنل مدیریت ثبت و نمایش داده می‌شود.
- موجودی به‌صورت اتمیک و ایمن در برابر هم‌زمانی کم/زیاد می‌شود (هم برای محصول ساده و هم برای هر ترکیب متغیر جداگانه).

### ۱۰.۴ چک‌لیست تست پیشنهادی

بعد از Deploy، این جریان‌ها را دستی امتحان کنید:

1. یک محصول متغیر (مثلاً «قاب سیلیکونی») بخرید: برند/مدل/رنگ را عوض کنید و ببینید قیمت، موجودی و تصویر درست به‌روز می‌شوند؛ یک ترکیب ناموجود را انتخاب کنید و مطمئن شوید دکمه‌ی افزودن غیرفعال است.
2. سفارش را به‌صورت «مهمان» (بدون ورود) با پرداخت کارت‌به‌کارت ثبت کنید؛ آدرس صفحه‌ی پرداخت را کپی و بدون پارامتر `?t=...` در یک مرورگر Incognito باز کنید — باید ۴۰۴/دسترسی غیرمجاز بدهد.
3. با پارامتر `?t=...` درست، رسید را آپلود کنید؛ در پنل مدیریت بررسی کنید سفارش هنوز «در انتظار پرداخت» است (تأیید خودکار نشده).
4. از پنل رسید را تأیید کنید؛ وضعیت سفارش باید به «پرداخت‌شده» تغییر کند و در جزئیات سفارش، برچسب رنگ/مدل انتخابی مشتری نمایش داده شود.
5. با یک کاربر دیگر (یا بدون ورود و بدون توکن درست) تلاش کنید تصویر رسید یا صفحه‌ی پرداخت سفارش فرد دیگری را ببینید — باید رد شود.
6. موجودی محصول ساده و موجودی همان ترکیب متغیر را پیش و پس از خرید و پس از لغو سفارش (که باید موجودی را برگرداند) بررسی کنید.

### ۱۰.۵ محدودیت این محیط توسعه

این نسخه در یک محیط Sandbox بدون دسترسی به اینترنت/رجیستری npm و بدون دیتابیس PostgreSQL زنده توسعه داده شده، بنابراین **اجرای واقعی `npm install` و `npm run build` در این محیط ممکن نبوده است**. به‌جای آن، تمام فایل‌های تغییریافته با بررسی دستی (تطبیق نام فیلدها با `schema.prisma`، بررسی Import‌ها، تعادل آکولاد/پرانتز، و اجرای TypeScript Compiler به‌صورت مجزا روی فایل‌های اصلی) بازبینی شدند؛ در همین بازبینی یک باگ واقعی (نام‌گذاری نادرست فیلد در فراخوانی درگاه پرداخت) پیدا و اصلاح شد. لطفاً پیش از استفاده در Production، حتماً یک‌بار `npm install && npm run build` را روی سرور یا محیط توسعه‌ی خودتان اجرا کنید تا از عبور کامل از Build اطمینان حاصل کنید.

## ۱۱. اصلاحات این نسخه: تراکنش‌های اتمیک، امنیت پیگیری سفارش، هم‌زمانی، رزرو موجودی، وابستگی‌ها

### ۱۱.۱ اتمیک‌سازی ثبت سفارش

ایجاد سفارش، ایجاد آیتم‌ها، کسر موجودی (محصول ساده و هر ترکیب متغیر) و افزایش شمارنده‌ی مصرف کد تخفیف، همگی حالا داخل **یک تراکنش دیتابیس واحد** (`db.$transaction`) در `app/api/checkout/route.ts` انجام می‌شوند. اگر هر مرحله شکست بخورد (مثلاً موجودی هم‌زمان توسط سفارش دیگری تمام شود، یا ظرفیت کد تخفیف هم‌زمان تکمیل شود)، **کل تراکنش** — از جمله سفارش و آیتم‌های همان لحظه ساخته‌شده و هر کسر موجودی قبلی در همان حلقه — به‌طور خودکار Rollback می‌شود؛ دیگر هیچ سفارش نیمه‌کاره یا موجودی نیمه‌کسرشده باقی نمی‌ماند. همچنین اگر سبد خرید (به هر دلیل، مثلاً باگ کلاینت یا درخواست دستکاری‌شده) شامل دو ردیف کاملاً یکسان (همان محصول + همان ترکیب) باشد، پیش از پردازش با هم جمع می‌شوند تا به‌جای دو ردیف سفارش و دو کسر موجودی جداگانه، یک ردیف صحیح ثبت شود.

### ۱۱.۲ امنیت صفحه‌ی پیگیری سفارش مهمان

پیش از این، فرم «پیگیری سفارش» (`/order/track`) با شماره سفارش + شماره موبایل، جزئیات کامل هر سفارشی — حتی سفارش‌های متصل به یک حساب کاربری — را نشان می‌داد؛ یعنی نقش «ورود به حساب» برای آن دسته سفارش‌ها را دور می‌زد. اصلاح شد:

- سفارش‌هایی که به یک **حساب کاربری** متصل‌اند، از این فرم عمومی هرگز نمایش داده نمی‌شوند؛ پیام «برای مشاهده جزئیات وارد حساب کاربری خود شوید» به همراه لینک ورود نشان داده می‌شود. جزئیات این سفارش‌ها فقط از طریق Session معتبر همان کاربر (`/account/orders/...`) قابل مشاهده است.
- سفارش‌های **مهمان** همچنان از طریق شماره سفارش + موبایل قابل پیگیری‌اند (چون حسابی برای ورود وجود ندارد)، اما این جست‌وجو حالا **محدود به تعداد تلاش** است (مدل جدید `TrackLookupAttempt`؛ حداکثر ۸ تلاش در هر ۱۵ دقیقه برای هر شماره سفارش) تا حدس‌زدن شماره موبایل با تلاش پیاپی عملاً غیرممکن شود.
- این یک تصمیم امنیتی آگاهانه است، نه یک راه‌حل کامل: شماره سفارش + موبایل هم‌ارز «توکن امن» نیست، اما با محدودیت تلاش، ریسک آن به‌طور محسوس کاهش می‌یابد و تجربه‌ی کاربری «پیگیری بدون حساب کاربری» حفظ می‌شود. اگر می‌خواهید این مسیر را کاملاً حذف و فقط لینک توکن‌دار (`?t=...`) را معیار دسترسی مهمان قرار دهید، `lib/trackLookup.ts` نقطه‌ی شروع تغییر است.

### ۱۱.۳ ایمنی در برابر هم‌زمانی و درخواست‌های تکراری

- **تأیید رسید کارت‌به‌کارت:** حالا علاوه بر Claim کردن خود رسید داخل تراکنش، وضعیت سفارش هم با یک `updateMany` شرطی (`status: PENDING_PAYMENT`) تغییر می‌کند؛ یعنی اگر سفارش در همین فاصله (مثلاً به‌خاطر انقضای رزرو) لغو شده باشد، تأیید یک رسید قدیمی دیگر نمی‌تواند آن را دوباره «پرداخت‌شده» کند — کل تراکنش با خطا Rollback می‌شود.
- **لغو سفارش و بازگشت موجودی:** منطق مشترک `cancelOrderAtomic()` (در `lib/orderLifecycle.ts`) اضافه شد که لغو سفارش را با الگوی Claim (`status: { not: CANCELED }`) و بازگشت موجودی را در یک تراکنش انجام می‌دهد؛ اگر دو مسیر مختلف (مثلاً ادمین و اسکریپت آزادسازی رزرو) هم‌زمان همان سفارش را لغو کنند، فقط یکی موجودی را برمی‌گرداند و دیگری بی‌اثر (No-op) می‌ماند — بدون خطر بازگشت دوباره‌ی موجودی.
- **Callback زرین‌پال:** پیش از فراخوانی درگاه برای Verify، سفارش با یک قفل شرطی (`paymentLockedAt`) Claim می‌شود؛ اگر همین Callback دو بار (مثلاً توسط خود درگاه یا رفرش کاربر) هم‌زمان فراخوانی شود، فقط یکی از آن‌ها واقعاً Verify و موجودی/وضعیت را تغییر می‌دهد و بقیه فقط آخرین وضعیت را گزارش می‌کنند. قفل‌های باقی‌مانده از یک تلاش ناموفق (مثلاً کرش سرور وسط Verify) بعد از ۲ دقیقه قابل تصاحب مجدد‌اند تا سفارش برای همیشه گیر نکند.

### ۱۱.۴ مدت رزرو موجودی برای سفارش‌های کارت‌به‌کارت

هر سفارش کارت‌به‌کارت هنگام ثبت یک `reservationExpiresAt` می‌گیرد — پیش‌فرض **۲۴ ساعت** از لحظه‌ی ثبت (قابل تغییر با متغیر محیطی `CARD_TRANSFER_HOLD_HOURS`، در `lib/reservation.ts`). این زمان در پنل مدیریت (جزئیات سفارش) و در صفحه‌ی پرداخت کارت‌به‌کارت مشتری نمایش داده می‌شود.

**آزادسازی خودکار موجودی پس از انقضا خودکار نیست** — باید اسکریپت زیر را زمان‌بندی (Cron) کنید:

```bash
npm run release-expired-reservations
# یا مستقیم:
npx tsx scripts/releaseExpiredReservations.ts
```

نمونه Cron (هر ۱۵ دقیقه):
```
*/15 * * * * cd /path/to/caseline-shop && npm run release-expired-reservations >> /var/log/caseline-release.log 2>&1
```

این اسکریپت سفارش‌های کارت‌به‌کارتِ «در انتظار پرداخت» که از زمان انقضایشان گذشته را پیدا کرده، با همان منطق اتمیک `cancelOrderAtomic()` لغو می‌کند و موجودی را برمی‌گرداند — هم‌زمانی‌ایمن، حتی اگر یک ادمین دقیقاً همان لحظه همان سفارش را دستی لغو کند.

### ۱۱.۵ بررسی امنیتی وابستگی‌ها (Dependencies)

این محیط توسعه به رجیستری npm دسترسی ندارد، بنابراین `npm audit` واقعی قابل اجرا نبود. بر اساس دانش موجود، مهم‌ترین مورد شناسایی‌شده:

- **Next.js:** نسخه‌ی قبلی پروژه (`14.2.15`) پیش از نسخه‌ای بود که یک آسیب‌پذیری شناخته‌شده و **حیاتی** در Middleware (دور زدن احراز هویت با هدر `x-middleware-subrequest`) را برطرف می‌کند — دقیقاً همان مکانیزمی که `middleware.ts` این پروژه برای محافظت از `/admin` و `/account` استفاده می‌کند. نسخه‌ی Next.js در `package.json` به `^14.2.25` (اولین نسخه‌ی ۱۴.۲ دارای این اصلاح) ارتقا یافت.
- سایر وابستگی‌ها (`next-auth`, `bcryptjs`, `zod`, `nanoid`, `@prisma/client`/`prisma`, و ابزارهای Dev) به بازه‌ی Caret (`^`) تغییر کردند تا `npm install` جدیدترین Patch سازگار هر بسته را از رجیستری واقعی (که روی سرور شما در دسترس است) دریافت کند، به‌جای نسخه‌های ثابت قدیمی.
- **حتماً پس از دریافت پروژه** دستور زیر را اجرا کنید تا آخرین Patchهای امنیتی واقعاً نصب شوند:
  ```bash
  npm install
  npm audit fix
  ```
  و در صورت گزارش شدن هر مورد High/Critical توسط `npm audit`، پیش از استقرار در Production بررسی و رفع کنید.

## ۱۳. شروع «پرامپت جامع» — حالت تاریک، بازآرایی صفحه محصول، لیست علاقه‌مندی‌ها

این بخش شروع فاز ۱ و ۲ پرامپت جامع توسعه را مستند می‌کند (فهرست کامل وضعیت هر فاز در `PROGRESS.md`).

### ۱۳.۱ مهاجرت دیتابیس لازم برای این نسخه

این نسخه مدل‌ها/فیلدهای جدید زیر را به Schema اضافه کرده — **مهاجرت جدید لازم است**، قبل از هر چیز حتماً بکاپ بگیرید:
- `WishlistItem` (لیست علاقه‌مندی‌ها)
- `Review` (نظرات کاربران)
- `OrderStatusHistory` (تاریخچه‌ی واقعی وضعیت سفارش)
- `User.myBrandId` / `User.myPhoneModelId` («گوشی من»)
- `PartnerApplication` و `User.isWholesale` (درخواست همکاری عمده/نمایندگی)
- `Product.wholesalePrice` و `ProductVariant.wholesalePrice` (قیمت عمده — ستون‌های Int اختیاری، بدون مقدار پیش‌فرض؛ توضیح کامل در ۱۳.۱۱)
- `Order.trackingCarrier` / `Order.trackingNumber` / `Order.refundedToWalletAt` (رهگیری مرسوله و بازگشت وجه — توضیح در ۱۳.۱۲ و ۱۳.۱۳)
- `User.walletBalance` / `User.loyaltyPoints`، مدل‌های جدید `WalletTransaction` و `LoyaltyTransaction`، و مقدار جدید `WALLET` در enum `PaymentMethod` (کیف پول و باشگاه مشتریان — توضیح در ۱۳.۱۳)
```bash

npx prisma migrate dev --name add_wishlist_reviews_timeline_myphone_partners_wholesale_pricing_tracking_wallet
# یا در Production:
npx prisma migrate deploy
```
اگر یکی از مهاجرت‌های قبلی این پروژه (`..._wholesale_pricing` یا نسخه‌های قبل‌تر) را از قبل اجرا کرده‌اید، کافی است یک بار دیگر `npx prisma migrate dev --name add_tracking_wallet_loyalty` را اجرا کنید تا فقط ستون‌ها/مدل‌های جدید این دور اضافه شوند.

### ۱۳.۲ حالت تاریک (Dark Mode)

دکمه‌ی ماه/خورشید در هدر سایت، بین حالت روشن و تاریک جابه‌جا می‌کند. انتخاب کاربر در مرورگرش ذخیره می‌شود (`localStorage`)؛ اگر کاربر تا حالا انتخابی نکرده باشد، از تنظیمات سیستم‌عامل او پیروی می‌کند. تمام رنگ‌های پروژه از طریق متغیرهای CSS در `app/globals.css` تعریف شده‌اند، بنابراین هیچ کامپوننتی نیازی به تغییر جداگانه نداشت.

### ۱۳.۳ بازآرایی صفحه محصول

در صفحه‌ی هر محصول (ساده و متغیر)، اطلاعات اصلیِ خرید (تصویر، قیمت، گزینه‌ها، دکمه‌ی افزودن به سبد) بالای صفحه ماندند و توضیحات/مشخصات/شرایط ارسال-بازگشت به یک آکاردئون قابل‌جمع‌شدن منتقل شدند. در نمای موبایل یک نوار پایین‌چسبان با قیمت و دکمه‌ی خرید هم اضافه شد.

### ۱۳.۴ لیست علاقه‌مندی‌ها (Wishlist)

کاربران واردشده می‌توانند با کلیک روی آیکون قلب در صفحه‌ی هر محصول، آن را به لیست علاقه‌مندی‌های خود اضافه/حذف کنند. لیست کامل در «حساب کاربری ← علاقه‌مندی‌ها» (`/account/wishlist`) قابل مشاهده است. این لیست به حساب کاربری متصل است (نه مرورگر)، تا بین دستگاه‌های مختلف یکسان بماند — برای استفاده از آن باید وارد حساب شوید؛ در غیر این صورت با کلیک روی قلب به صفحه‌ی ورود هدایت می‌شوید.

### ۱۳.۵ نظرات کاربران (Reviews)

در پایین صفحه‌ی هر محصول، بخش «نظرات کاربران» اضافه شد. هر کاربر واردشده می‌تواند یک امتیاز (۱ تا ۵ ستاره) و یک نظر متنی برای هر محصول ثبت کند (ارسال دوباره، نظر قبلی‌اش را جایگزین می‌کند، نه اینکه تکراری اضافه شود). برچسب «خرید تأییدشده» به‌صورت خودکار و صرفاً بر اساس سابقه‌ی سفارش‌های واقعی و پرداخت‌شده‌ی همان کاربر برای همان محصول محاسبه می‌شود — از سمت کاربر قابل‌تنظیم نیست. **هیچ نظر یا امتیاز ساختگی/Seed‌شده‌ای در پروژه وجود ندارد** — طبق دستور صریح پرامپت جامع مبنی بر ممنوعیت نظرات/آمار ساختگی، این بخش تا وقتی کاربران واقعی نظر ندهند، کاملاً خالی نمایش داده می‌شود.

### ۱۳.۶ تاریخچه‌ی واقعی وضعیت سفارش (Order Timeline)

مدل جدید `OrderStatusHistory` یک رکورد واقعی و append-only از هر تغییر وضعیت سفارش ثبت می‌کند (زمان دقیق + یادداشت کوتاه، مثلاً «ثبت سفارش»، «پرداخت آنلاین تأیید شد»، «رسید کارت‌به‌کارت توسط مدیر تأیید شد»، «مهلت رزرو موجودی به پایان رسید»). این رکوردها همیشه در همان تراکنش دیتابیسی نوشته می‌شوند که خودِ فیلد `status` را تغییر می‌دهد، پس هرگز از واقعیت عقب نمی‌مانند. یک نمای Timeline (`components/OrderTimeline.tsx`) این تاریخچه را در سه صفحه نمایش می‌دهد: صفحه‌ی سفارش در حساب کاربری، صفحه‌ی پیگیری مهمان، و صفحه‌ی سفارش در پنل ادمین. **هیچ مرحله‌ی نمایشی/ساختگی‌ای وجود ندارد** — سفارشی که هنوز به یک مرحله نرسیده، صرفاً هیچ ردیفی برای آن مرحله ندارد (نه یک آیکون خاکستری تزئینی).

### ۱۳.۷ «گوشی من»

در حساب کاربری، بخش «گوشی من» به کاربر اجازه می‌دهد برند و مدل گوشی خودش را یک‌بار ذخیره کند (`components/MyPhoneForm.tsx`، `lib/actions/myPhone.ts`). این انتخاب در دو جا استفاده می‌شود:
1. در صفحه‌ی هر محصول متغیر، گزینه‌ی برند/مدل مطابق «گوشی من» به‌صورت خودکار از قبل انتخاب می‌شود (کاربر همچنان می‌تواند آزادانه تغییرش دهد).
2. در صفحه‌ی دسته‌بندی و نتایج جستجو، وقتی کاربر «گوشی من» را ذخیره کرده باشد، یک گزینه‌ی فیلتر «فقط سازگار با گوشی من» ظاهر می‌شود که فقط محصولات واقعاً سازگار (محصول ساده با همان مدل، یا محصول متغیر که حداقل یک ترکیب فعال برای همان مدل دارد) را نشان می‌دهد.

### ۱۳.۸ مقایسه محصولات (Compare)

روی هر کارت محصول، آیکون مقایسه (دو مربع هم‌پوشان) قابل کلیک است — تا ۴ محصول هم‌زمان قابل انتخاب است (لیست در مرورگر کاربر، بدون نیاز به ورود به حساب کاربری، مشابه سبد خرید). صفحه‌ی `/compare` محصولات انتخاب‌شده را در یک جدول کنار هم نشان می‌دهد: قیمت، دسته‌بندی، برند، موجودی، و مشخصات فنی. مشخصات فنی از یک فیلد جدید در فرم محصول پنل ادمین («مشخصات فنی») می‌آید — هر خط به‌صورت «عنوان: مقدار»؛ محصولی که مشخصاتش پر نشده، فقط ردیف‌های عمومی (قیمت/دسته/برند/موجودی) را در جدول دارد، نه ردیف‌های خالی یا ساختگی.

### ۱۳.۹ همکاری عمده‌فروشی/نمایندگی — فقط گردش‌کار درخواست/تأیید (نه کل فاز ۳)

صفحه‌ی عمومی `/partners` یک فرم درخواست همکاری نمایش می‌دهد (نیازمند ورود به حساب کاربری — تا هر درخواست دقیقاً به یک حساب واقعی متصل باشد). ادمین در `/admin/partners` درخواست‌ها را می‌بیند و تأیید/رد می‌کند؛ تأیید یک درخواست، فیلد `User.isWholesale` را روی حساب همان کاربر `true` می‌کند (تنها مسیر کد در کل پروژه که این فیلد را ست می‌کند).

**⚠️ این یک زیرمجموعه‌ی محدود از فاز ۳ پرامپت جامع است، نه کل آن.** آنچه هنوز پیاده نشده و به‌عنوان کار باقی‌مانده در `PROGRESS.md` ثبت شده: پنل اختصاصی همکار (سفارش‌دهی عمده، صورتحساب)، و حداقل سفارش/تخفیف پلکانی. (قیمت‌گذاری ویژه‌ی عمده اکنون پیاده شده — بخش ۱۳.۱۱ را ببینید.)

### ۱۳.۱۱ قیمت‌گذاری عمده (Wholesale Pricing) — تکمیل بخش قیمت از فاز ۳

هر محصول و هر ترکیب (Variant) یک فیلد اختیاری «قیمت عمده‌فروشی» در فرم ادمین دارد (`components/admin/ProductForm.tsx`, `components/admin/VariantForm.tsx`). این قیمت **فقط** وقتی به مشتری نشان داده و از او دریافت می‌شود که هر دو شرط برقرار باشد:
1. کاربر واردشده، یک همکار تأییدشده باشد (`User.isWholesale === true` — تنها از طریق تأیید درخواست در `/admin/partners`).
2. همان محصول/ترکیب مشخص، یک `wholesalePrice` واقعی از طرف ادمین داشته باشد.

اگر هرکدام از این دو برقرار نباشد، قیمت عادی (retail) بدون هیچ تخفیف حدسی یا درصدی نمایش داده می‌شود — هیچ محاسبه‌ی خودکار تخفیف وجود ندارد، فقط عددی که ادمین مستقیماً وارد کرده. منطق در `lib/wholesalePricing.ts` (`isViewerWholesale()`, `effectivePrice()`) متمرکز شده و در همه‌ی سطوح زیر اعمال می‌شود:
- صفحه‌ی اصلی، صفحه‌ی دسته‌بندی، نتایج جستجو، صفحه‌ی محصول (ساده و متغیر)، محصولات مرتبط، لیست علاقه‌مندی‌ها، و صفحه‌ی مقایسه — همه قیمت مؤثر (retail یا wholesale، بسته به کاربر) را نمایش می‌دهند؛ اگر قیمت عمده اعمال شود، «قیمت قبلی» (تخفیف retail) به‌جای نمایش گمراه‌کننده، مخفی می‌شود.
- **نقطه‌ی نهایی و معتبر قیمت‌گذاری، `app/api/checkout/route.ts` است** — قیمت هر خط سفارش، صرف‌نظر از هرچه در مرورگر مشتری نمایش داده شده، دوباره از دیتابیس و وضعیت واقعی `isWholesale` کاربر (نه چیزی که کلاینت ارسال کرده) محاسبه می‌شود. این دقیقاً همان الگوی «هرگز به قیمت ارسالی از کلاینت اعتماد نکن» است که از ابتدا در این فایل رعایت شده.

آنچه هنوز کار نمی‌کند و در PROGRESS.md به‌عنوان باقی‌مانده ثبت شده: تخفیف پلکانی بر اساس تعداد، حداقل سفارش برای همکاران، و لیست قیمت جداگانه/دانلودی برای همکاران (فعلاً فقط همان قیمت‌های تک‌محصولی که ادمین وارد کرده اعمال می‌شود).

**تست‌نشده (نیازمند اجرای واقعی):**
- تأیید یک درخواست همکاری واقعی در `/admin/partners`، سپس ورود با همان حساب و بررسی اینکه قیمت محصولاتی که برایشان `wholesalePrice` تنظیم شده، در تمام صفحات بالا واقعاً به قیمت عمده تغییر می‌کند — و محصولاتی که `wholesalePrice` ندارند، همچنان قیمت عادی را نشان می‌دهند.
- تکمیل یک خرید واقعی با همان حساب همکار و بررسی این‌که مبلغ نهایی سفارش (در دیتابیس، نه فقط نمایش صفحه) واقعاً بر اساس قیمت عمده محاسبه شده است.

### ۱۳.۱۰ تست‌نشده در این نسخه (نیازمند اجرای واقعی)

- اجرای واقعی `npx prisma migrate dev` روی یک دیتابیس PostgreSQL واقعی.
- رفتار حالت تاریک/روشن در مرورگرهای واقعی (Chrome/Safari/Firefox، دسکتاپ و موبایل).
- افزودن/حذف واقعی از لیست علاقه‌مندی‌ها با یک حساب کاربری واقعی، و بررسی درست‌بودن نمایش اولیه‌ی قلب (پر/خالی) پس از رفرش صفحه.
- ثبت نظر واقعی با یک حساب کاربری که واقعاً آن محصول را خریده، و بررسی اینکه برچسب «خرید تأییدشده» درست نمایش داده می‌شود.
- بررسی نمایش صحیح Timeline سفارش پس از هر مرحله‌ی واقعی (ثبت → پرداخت → آماده‌سازی → ارسال → تحویل، یا لغو) در هر سه صفحه‌ی ذکرشده در ۱۳.۶.
- ذخیره‌ی «گوشی من» و بررسی این‌که در صفحه‌ی یک محصول متغیر واقعاً پیش‌انتخاب می‌شود، و فیلتر «فقط سازگار با گوشی من» در دسته‌بندی/جستجو نتایج درستی برمی‌گرداند.
- افزودن ۲ تا ۴ محصول به مقایسه از صفحه‌ی اصلی/دسته‌بندی، و بررسی صحت جدول در `/compare` — به‌خصوص پس از پر کردن «مشخصات فنی» یک محصول در پنل ادمین.
- ارسال یک درخواست همکاری از `/partners` با یک حساب کاربری آزمایشی، و بررسی این‌که تأیید آن در `/admin/partners` واقعاً `isWholesale` را روی همان کاربر true می‌کند (قابل بررسی در Prisma Studio).

دستور تست دستی پس از migrate و اجرای `npm run dev`:
```
1. وارد حساب کاربری شوید (یا ثبت‌نام کنید).
2. به صفحه‌ی یک محصول بروید و روی آیکون قلب کلیک کنید — باید پر شود.
3. صفحه را رفرش کنید — قلب باید همچنان پر بماند (یعنی وضعیت از سرور خوانده شده، نه فقط حافظه‌ی مرورگر).
4. به /account/wishlist بروید — محصول باید در لیست باشد.
5. از همان صفحه یا صفحه محصول، دوباره روی قلب کلیک کنید — باید حذف شود.
```

### ۱۳.۱۲ رهگیری واقعی مرسوله (Shipment Tracking) — تکمیل فاز ۴

مدیر می‌تواند برای هر سفارش، نام شرکت پستی و کد رهگیری واقعی را در صفحه‌ی سفارش پنل ادمین (`/admin/orders/[id]`) وارد کند. **هیچ اتصال زنده‌ای به هیچ شرکت پستی وجود ندارد** — این صرفاً یک فیلد متنی است که مدیر خودش پر می‌کند (دقیقاً همان چیزی که در رسید/برگه‌ی پستی واقعی درج شده)، نه یک وضعیت زنده‌ی ردیابی‌شده. این اطلاعات، وقتی ثبت شود:
- در صفحه‌ی سفارش داخل حساب کاربری مشتری (`/account/orders/[id]`) نمایش داده می‌شود.
- در صفحه‌ی پیگیری عمومی مهمان (`/order/track`) هم نمایش داده می‌شود.
- یک ردیف در تاریخچه‌ی واقعی وضعیت سفارش (`OrderStatusHistory`) هم ثبت می‌شود (نه یک تغییر وضعیت، بلکه یک یادداشت واقعی هم‌زمان با وضعیت فعلی سفارش).

**تست‌نشده (نیازمند اجرای واقعی):** وارد کردن یک نام شرکت پستی و کد رهگیری برای یک سفارش واقعی در پنل ادمین، و بررسی این‌که در هر سه صفحه‌ی بالا (حساب کاربری، پیگیری مهمان، Timeline) درست نمایش داده می‌شود.

### ۱۳.۱۳ کیف پول و باشگاه مشتریان — شروع فاز ۵ (بدون شارژ مستقیم)

**⚠️ طبق دستور صریح پرامپت جامع، امکان شارژ واقعی کیف پول (Top-up) عمداً غیرفعال است** — چون هیچ درگاه پرداختی برای شارژ کیف پول در این پروژه متصل/تست نشده و افزودن دکمه‌ی «شارژ کیف پول» بدون درگاه واقعی پشت آن، دقیقاً همان «دکمه‌ی تزئینی» ممنوع‌شده است. در عوض، موجودی کیف پول **فقط** از این دو مسیر واقعی افزایش می‌یابد:
1. **بازگشت وجه سفارش توسط مدیر:** در صفحه‌ی هر سفارشِ واقعاً پرداخت‌شده (`PAID` به بعد) در پنل ادمین، دکمه‌ی «لغو سفارش و بازگشت وجه به کیف پول» ظاهر می‌شود. این کار سفارش را لغو می‌کند، موجودی کالاها را به انبار برمی‌گرداند (دقیقاً مثل لغو معمولی)، و مبلغ کامل سفارش را به کیف پول همان مشتری واریز می‌کند — همه در یک تراکنش اتمیک، با یک فیلد `Order.refundedToWalletAt` که تضمین می‌کند هر سفارش فقط یک‌بار قابل بازگشت وجه است.
2. **اصلاحیه‌ی دستی مدیر:** در صفحه‌ی هر کاربر در پنل ادمین (`/admin/users/[id]`)، مدیر می‌تواند با وارد کردن یک دلیل الزامی، مبلغی را به کیف پول کاربر اضافه یا از آن کسر کند (مثلاً جبران خسارت، اصلاح اشتباه). هر تغییر، چه از مسیر بازگشت وجه چه اصلاحیه‌ی دستی، در یک دفترکل واقعی و تغییرناپذیر (`WalletTransaction`) ثبت می‌شود که مشتری هم آن را در `/account/wallet` می‌بیند.

موجودی کیف پول را می‌توان هنگام تکمیل خرید مصرف کرد: در صفحه‌ی Checkout، اگر کاربر وارد حساب کاربری شده باشد و موجودی کیف پولش **کل مبلغ سفارش را پوشش دهد**، گزینه‌ی «پرداخت از کیف پول» ظاهر می‌شود؛ در غیر این صورت (موجودی صفر یا ناکافی)، این گزینه اصلاً نمایش داده نمی‌شود یا غیرفعال است. با انتخاب این گزینه، سفارش بلافاصله و به‌طور کامل پرداخت‌شده ثبت می‌شود (بدون نیاز به درگاه یا رسید) — کسر موجودی کیف پول هم مثل قیمت‌گذاری عمده، **دوباره و مستقل از هر چیزی که کلاینت فرستاده**، از دیتابیس محاسبه و به‌صورت اتمیک (با محافظت در برابر هم‌زمانی، مشابه الگوی موجودی/کد تخفیف) کسر می‌شود.

**باشگاه مشتریان (امتیاز):** به ازای هر سفارش واقعی که به وضعیت `PAID` می‌رسد (از هر مسیر: زرین‌پال، تأیید رسید کارت‌به‌کارت، تغییر دستی وضعیت توسط مدیر، یا پرداخت کامل از کیف پول)، ۱ امتیاز به ازای هر ۱۰٬۰۰۰ تومان به کاربر تعلق می‌گیرد. این هم یک دفترکل واقعی دارد (`LoyaltyTransaction`) که `orderId` آن `@unique` است — یعنی حتی اگر وضعیت یک سفارش چندبار بررسی/تغییر کند، هرگز بیش از یک‌بار برای همان سفارش امتیاز داده نمی‌شود. موجودی و تاریخچه‌ی امتیاز در `/account/wallet` قابل مشاهده است.

**آنچه هنوز پیاده نشده (باقی‌مانده‌ی فاز ۵):**
- تبدیل امتیاز باشگاه مشتریان به تخفیف یا محصول رایگان (فعلاً فقط انباشته می‌شود، مصرفی ندارد).
- ترکیب پرداخت جزئی از کیف پول + باقی از درگاه (فعلاً کیف پول فقط زمانی گزینه است که کل مبلغ را پوشش دهد).
- هرگونه شارژ مستقیم کیف پول توسط خود مشتری (عمداً و طبق دستور پرامپت جامع غیرفعال، تا زمان اتصال/تست یک درگاه واقعی برای این کار).

**تست‌نشده (نیازمند اجرای واقعی و دیتابیس زنده):**
- بازگشت وجه یک سفارش واقعاً پرداخت‌شده به کیف پول از پنل ادمین، و بررسی این‌که سفارش لغو و موجودی کالا بازگردانده شده، مبلغ درست به کیف پول مشتری اضافه شده، و دکمه‌ی بازگشت وجه دیگر برای همان سفارش ظاهر نمی‌شود.
- اصلاحیه‌ی دستی افزایش/کاهش موجودی کیف پول یک کاربر از `/admin/users/[id]`، و تلاش برای کسر مبلغی بیشتر از موجودی فعلی (باید با خطا رد شود).
- تکمیل یک خرید کامل با «پرداخت از کیف پول» وقتی موجودی دقیقاً کافی است، و بررسی این‌که سفارش بلافاصله `PAID` ثبت می‌شود، موجودی کیف پول کسر می‌شود، و امتیاز باشگاه مشتریان به‌درستی اضافه می‌شود.
- بررسی این‌که با موجودی ناکافی، گزینه‌ی کیف پول در Checkout اصلاً قابل انتخاب نیست.

### ۱۳.۱۴ شروع فاز ۶ — «مرکز فرماندهی» مدیریت: جستجوی سراسری، انبار، گزارش مالی

**⚠️ این یک زیرمجموعه‌ی محدود از فاز ۶ پرامپت جامع است، نه «پنل مدیریت کامل» توصیف‌شده در آن.** سه ابزار واقعی و کاملاً کارکردی اضافه شد:

- **جستجوی سراسری (`/admin/search`):** یک کادر جستجو در بالای تمام صفحات پنل مدیریت (دسکتاپ و موبایل) که هم‌زمان در محصولات (نام/SKU/اسلاگ)، سفارش‌ها (شماره سفارش/نام و شماره‌ی گیرنده)، و کاربران (نام/ایمیل/شماره) جستجوی واقعی (substring، بدون حساسیت به بزرگی/کوچکی حروف) انجام می‌دهد و نتایج را با لینک مستقیم به همان صفحه نشان می‌دهد. جستجوی فازی/تصحیح غلط تایپی یا رتبه‌بندی هوشمند وجود ندارد — فقط یک تطبیق مستقیم و واقعی روی دیتابیس.
- **انبار / موجودی کم (`/admin/inventory`):** فهرستی واقعی از محصولات ساده و ترکیب‌های فعالی که موجودی‌شان ۵ عدد یا کمتر است (آستانه‌ی ثابت، نه یک الگوریتم پیش‌بینی سرعت فروش)، مرتب از کم‌ترین موجودی، با لینک مستقیم به ویرایش همان مورد.
- **گزارش‌های مالی (`/admin/reports`):** درآمد و تعداد سفارش پرداخت‌شده‌ی ۳۰ روز اخیر (نمودار میله‌ای ساده، محاسبه‌شده مستقیماً از سفارش‌های واقعی با SQL خام `date_trunc`)، پرفروش‌ترین محصولات بر اساس تعداد فروش واقعی (نه یک لیست ویژه‌ی دستی)، و شکست تعداد سفارش‌ها بر اساس وضعیت (کل تاریخچه). همه‌ی اعداد این صفحه از `Order`/`OrderItem` واقعی محاسبه می‌شوند — هیچ عدد Placeholder یا تخمینی نیست.

**آنچه هنوز از فاز ۶ پیاده نشده:** داشبورد قابل شخصی‌سازی (Drag & Drop ویجت‌ها)، سامانه‌ی هشدار خودکار موجودی (ایمیل/پیامک هنگام رسیدن به آستانه)، گزارش‌های مالی پیشرفته‌تر (سود ناخالص بر اساس `costPrice`، مقایسه‌ی دوره‌به‌دوره)، و تنظیمات سراسری سایت (SEO عمومی، شبکه‌های اجتماعی و مانند آن — تنظیمات فعلی فقط محدود به کارت بانکی است).

**تست‌نشده (نیازمند دیتابیس و اجرای واقعی):** جستجوی یک محصول/سفارش/کاربر واقعی از کادر جستجوی پنل و بررسی درستی نتایج و لینک‌ها؛ بررسی این‌که صفحه‌ی انبار موجودی واقعی محصولات را نشان می‌دهد (با کم‌کردن دستی موجودی یک محصول در Prisma Studio تا زیر ۵ برود)؛ بررسی نمودار درآمد روزانه پس از ثبت چند سفارش واقعی پرداخت‌شده در تاریخ‌های مختلف.

### ۱۳.۱۵ شروع فاز ۷ — Page Builder بصری (سطح پایه، نه Drag & Drop کامل)

**⚠️ این یک زیرمجموعه‌ی محدود از فاز ۷ است، نه یک ابزار طراحی صفحه‌ی کامل با drag & drop و کتابخانه‌ی بلوک‌های متنوع.** آنچه اضافه شد یک نوع بخش جدید در همان سامانه‌ی مدیریت صفحه‌ی اصلی (`/admin/homepage`) است به نام **«بلوک محتوای دلخواه»**:

- بخش‌های ثابت صفحه‌ی اصلی (Hero، نوار دسته‌بندی، پرفروش‌ترین‌ها و…) همچنان فقط قابل ترتیب‌دهی/فعال‌-غیرفعال‌کردن هستند (بدون تغییر).
- «بلوک محتوای دلخواه» تنها نوع بخشی است که مدیر می‌تواند از صفر **بسازد، ویرایش کند، و حذف کند** — با عنوان، متن، تصویر (اختیاری)، و یک دکمه‌ی لینک‌دار (اختیاری). محتوا در ستون JSON عمومی `HomepageSection.config` ذخیره می‌شود (بدون نیاز به Migration جدید به‌ازای هر بلوک).
- می‌توان چندین بلوک دلخواه ساخت و مثل بقیه‌ی بخش‌ها در فهرست ترتیب‌دهی، جابه‌جا/فعال‌-غیرفعال کرد.

**تفاوت با یک Page Builder واقعی:** بدون canvas بصری، بدون drag & drop، بدون کتابخانه‌ی بلوک‌های متنوع (گالری تصویر، ویدیو، فرم، ستون‌بندی چندگانه) — فقط یک نوع بلوک ساده‌ی متن+تصویر+دکمه، که همان چیزی است که واقعاً در این نشست قابل تحویل صادقانه بود.

**تست‌نشده (نیازمند اجرای واقعی):** ساخت یک بلوک جدید از `/admin/homepage`، بررسی نمایش آن در صفحه‌ی اصلی با ترتیب درست، ویرایش محتوای آن، و حذف آن (و بررسی این‌که بعد از حذف دیگر در صفحه‌ی اصلی نمایش داده نمی‌شود).

### ۱۳.۱۶ رفع یک باگ واقعی: پیام‌های «تماس با ما» هرگز دیده نمی‌شدند

فرم عمومی `/contact` از قبل کاملاً کار می‌کرد و پیام‌ها را واقعاً در جدول `ContactMessage` ذخیره می‌کرد — اما **هیچ صفحه‌ای در پنل مدیریت برای دیدن این پیام‌ها وجود نداشت**، یعنی مشتری فکر می‌کرد پیامش ارسال شده (و واقعاً هم ذخیره می‌شد)، ولی هیچ‌کس هرگز آن را نمی‌خواند. این یک باگ واقعی بود که هنگام کار روی فاز ۸ پیدا و رفع شد: صفحه‌ی جدید `/admin/contact-messages` اضافه شد — فهرست همه‌ی پیام‌ها، با علامت‌گذاری خوانده‌شده/نشده.

### ۱۳.۱۷ شروع فاز ۸ — پشتیبانی دوطرفه (تیکت) و صفحات محتوایی ساده (CMS پایه)

**⚠️ این زیرمجموعه‌ای محدود از فاز ۸ است — نه بازاریابی خودکار (Email Marketing) و نه یک CMS کامل با بلوک‌های متنوع.**

**پشتیبانی (تیکت):** برخلاف فرم «تماس با ما» (که یک‌طرفه است)، این یک گفتگوی واقعی و دوطرفه است:
- مشتری وارد‌شده از `/account/support` تیکت جدید می‌سازد (`/account/support/new`) و می‌تواند در `/account/support/[id]` به پاسخ‌های پشتیبانی جواب بدهد.
- مدیر از `/admin/support` همه‌ی تیکت‌ها را می‌بیند (باز/پاسخ‌داده‌شده/بسته، مرتب‌شده تا تیکت‌های باز بالا باشند) و از `/admin/support/[id]` پاسخ می‌دهد یا تیکت را می‌بندد.
- وضعیت تیکت (`OPEN`/`ANSWERED`/`CLOSED`) یک بازتاب صادقانه از نوبت پاسخ است، نه یک گردش‌کار SLA پیچیده: پاسخ مشتری همیشه وضعیت را `OPEN` می‌کند (حتی اگر بسته بوده)، پاسخ مدیر آن را `ANSWERED` می‌کند، و فقط مدیر می‌تواند صریحاً ببندد.
- **فقط برای کاربران واردشده** — تیکت مهمان پشتیبانی نمی‌شود؛ کاربر مهمان همچنان از فرم «تماس با ما»ی موجود استفاده می‌کند.
- **نیازمند migrate جدید** (مدل‌های `SupportTicket`/`SupportMessage`).

**صفحات محتوایی (CMS پایه):** مدل جدید `Page` — مدیر از `/admin/pages` صفحات ثابت متنی (مثلاً حریم خصوصی، قوانین بیشتر، سوالات متداول) می‌سازد و در آدرس `/page/<اسلاگ>` منتشر می‌شود. متن به‌صورت ساده (پاراگراف‌به‌پاراگراف) نمایش داده می‌شود، **نه HTML خام** — تا هیچ محتوایی که مدیر تایپ می‌کند نتواند اسکریپت/مارک‌آپ را به سایت عمومی تزریق کند. صفحات ثابت قبلی (`/about`, `/terms`) دست‌نخورده باقی ماندند؛ این یک سامانه‌ی موازی برای صفحات *جدیدی* است که مدیر خودش می‌خواهد اضافه کند. **نیازمند migrate جدید** (مدل `Page`).

**آنچه هنوز از فاز ۸ پیاده نشده:** بازاریابی/ایمیل خودکار (چون هیچ سرویس ارسال ایمیل واقعی متصل/تست نشده — طبق همان اصل «هیچ دکمه‌ی تزئینی» که برای شارژ کیف پول هم رعایت شد)، ویرایشگر متن غنی (Rich Text/WYSIWYG) برای صفحات، نسخه‌بندی/زمان‌بندی انتشار صفحات، و دسته‌بندی/برچسب‌گذاری تیکت‌های پشتیبانی.

**تست‌نشده (نیازمند اجرای واقعی):**
- ثبت یک پیام واقعی از `/contact` و بررسی نمایش آن در `/admin/contact-messages`.
- ثبت یک تیکت واقعی از یک حساب کاربری، پاسخ مدیر از پنل، پاسخ دوباره‌ی مشتری، و بررسی این‌که وضعیت‌ها درست تغییر می‌کنند.
- تلاش یک کاربر برای دیدن تیکت کاربر دیگر با حدس‌زدن URL (باید ۴۰۴ بگیرد).
- ساخت یک صفحه‌ی محتوایی جدید از `/admin/pages` و بررسی نمایش صحیح آن در `/page/<اسلاگ>`، و این‌که یک صفحه‌ی «پیش‌نویس» (`isPublished=false`) در سایت عمومی ۴۰۴ می‌دهد.

### ۱۳.۱۸ شروع فاز ۹ — RBAC کارمندان + ورود دو مرحله‌ای (۲FA) + موتور اتوماسیون بدون‌کد

**نقش جدید STAFF:** علاوه بر CUSTOMER/ADMIN، حالا یک نقش سوم هست که مدیر (ADMIN) از `/admin/staff` می‌سازد — حساب کارمند فقط به بخش‌هایی از پنل دسترسی دارد که صراحتاً به او داده شده (فیلد `User.permissions`، آرایه‌ای از کلیدهای مجوز). **فعلاً تنها مجوز واقعی و اعمال‌شده «SUPPORT»** است (پشتیبانی و پیام‌های تماس با ما) — عمداً به همین یک مورد محدود شده تا هیچ چک‌باکسی تزئینی/بی‌اثر در پنل نباشد. اجرای این محدودیت در دو لایه‌ی مستقل انجام می‌شود:
1. **میان‌افزار (`middleware.ts`)**: فهرست `STAFF_ALLOWED` مشخص می‌کند کارمند فقط به کدام مسیرها (و با کدام مجوز) اجازه‌ی ورود دارد؛ هر مسیر دیگر زیر `/admin` (حتی اگر لینکش هم برایش نمایش داده نشود) کارمند را به صفحه‌ی ورود برمی‌گرداند.
2. **خود Server Action** (`requireStaffPermission` در `lib/actions/guard.ts`) — یک بررسی مستقل دوم، مستقل از میان‌افزار، دقیقاً مثل `requireAdmin` قبلی.

> 🐛 **باگ واقعی پیدا و رفع شد (در بازبینی کامل بعدی):** در همین دور که این ساختار ساخته شد، صفحات `/admin/support` و `/admin/contact-messages` درست برای کارمند در میان‌افزار باز شده بودند، اما خودِ Server Actionهای پشت دکمه‌های آن صفحات (`adminReplyToTicket`، `closeTicket` در `lib/actions/support.ts`، و `markContactMessageRead` در `lib/actions/contactMessages.ts`) هنوز `requireAdmin()` (فقط ADMIN) بودند، نه `requireStaffPermission("SUPPORT")`. نتیجه: یک کارمند با مجوز SUPPORT صفحه را می‌دید ولی با کلیک روی «ارسال پاسخ»، «بستن تیکت»، یا تغییر وضعیت خوانده‌شده، خطای «دسترسی غیرمجاز» می‌گرفت — یعنی این قابلیت در عمل برای کارمند کار نمی‌کرد، برخلاف چیزی که در همین بخش ادعا شده بود. هر سه اکشن اصلاح شدند تا از `requireStaffPermission("SUPPORT")` استفاده کنند (که ADMIN را هم همچنان می‌پذیرد). این مورد در یک بازبینی کامل و مستقل بعد از نوشتن کد اولیه پیدا شد، نه توسط تست دستی — دلیل دیگری برای این‌که این ویژگی هنوز «تست‌نشده» علامت‌گذاری شده باشد تا با یک حساب کارمند واقعی امتحان شود.
مدیر همیشه به همه‌جا دسترسی دارد (بدون نیاز به مجوز جداگانه). **نکته‌ی مهم:** تغییر دسترسی یک کارمند از نشست (Session) باز فعلی او فوراً اثر نمی‌گیرد — چون مجوزها داخل JWT ذخیره می‌شوند، فقط از ورود بعدی او اعمال می‌شود (مثل تغییر نقش در بیشتر پیاده‌سازی‌های NextAuth با استراتژی JWT).

**ورود دو مرحله‌ای (۲FA، فقط برای ADMIN/STAFF):** پیاده‌سازی کامل و واقعی الگوریتم TOTP طبق RFC 6238 (`lib/totp.ts`) — **بدون هیچ کتابخانه‌ی جدید**، فقط با ماژول داخلی `crypto` نود، چون این Sandbox نمی‌تواند `npm install` را برای تأیید یک بسته‌ی جدید (مثل otplib) واقعاً اجرا کند. سازگار با هر اپلیکیشن احراز هویت استاندارد (Google Authenticator، Authy، …). از `/admin/security`:
- شروع راه‌اندازی → یک کلید تصادفی ساخته و **نه فعال** ذخیره می‌شود.
- کاربر کلید را به‌صورت دستی در اپ احراز هویت وارد می‌کند (⚠️ **این پروژه تصویر QR نمی‌سازد** — دلیل دقیقاً همان است: افزودن یک کتابخانه‌ی تولید QR قابل تأیید در این Sandbox نبود؛ وارد کردن دستی کلید در هر اپ استانداردی کار می‌کند).
- کاربر یک کد ۶ رقمی واقعی وارد می‌کند؛ فقط پس از تأیید موفق، `twoFactorEnabled` به `true` تغییر می‌کند — یعنی یک راه‌اندازی نیمه‌کاره هرگز نمی‌تواند کسی را قفل کند یا بی‌خبر اعمال شود.
- غیرفعال‌سازی به وارد کردن دوباره‌ی رمز عبور نیاز دارد (نه فقط داشتن نشست باز).
- در ورود (`/admin/login`)، بعد از ایمیل/رمز درست، اگر ۲FA فعال باشد یک فیلد کد نمایش داده می‌شود؛ `authorize()` در `lib/auth.ts` خطای مشخص `"2FA_REQUIRED"` می‌دهد که صفحه‌ی ورود دقیقاً همین رشته را تشخیص می‌دهد.

**موتور اتوماسیون بدون‌کد (`/admin/automation`):** یک قانون یعنی «رویداد واقعی → کار واقعی»، بدون نوشتن کد:
- رویدادهای پشتیبانی‌شده (هر سه، نقطه‌ی وقوع واقعی در کد): `ORDER_DELIVERED` (تغییر دستی وضعیت سفارش به تحویل‌شده در `updateOrderStatus`)، `NEW_SUPPORT_TICKET` (`createTicket`)، `NEW_CONTACT_MESSAGE` (`POST /api/contact`).
- کارهای پشتیبانی‌شده: `CREATE_ADMIN_ALERT` (ساخت یک ردیف واقعی در مدل جدید `AdminAlert`، نمایش در `/admin/alerts` + یک نشان زنگ در بالای پنل) و `GRANT_LOYALTY_BONUS` (فقط برای `ORDER_DELIVERED`؛ یک `LoyaltyTransaction` واقعی با کلید یکتای `<orderId>:automation:<ruleId>` می‌سازد تا اجرای دوباره‌ی رویداد هرگز پاداش را دوبار ندهد).
- **هیچ کار «ارسال ایمیل/پیامک» وجود ندارد** — چون هیچ سرویس ارسال واقعی به این پروژه متصل/تست نشده؛ افزودن چنین گزینه‌ای بدون سرویس پشت آن دقیقاً همان دکمه‌ی تزئینی‌ای می‌شد که این پروژه صریحاً ممنوع کرده.
- اجرای قوانین (`lib/automation.ts`) همیشه داخل همان تراکنش (`$transaction`) رویداد اصلی صدا زده می‌شود — یعنی اگر رویداد اصلی Rollback شود، اثر اتوماسیون هم Rollback می‌شود.

**نیازمند migrate جدید** (`Role.STAFF`، `User.permissions/twoFactorSecret/twoFactorEnabled`، مدل‌های `AutomationRule`/`AdminAlert`).

**آنچه هنوز پیاده نشده:** هیچ شرط پیچیده‌ای روی قوانین اتوماسیون (فقط رویداد+کار ساده، بدون فیلتر/AND-OR)، هیچ اقدام مبتنی بر ایمیل/پیامک، تصویر QR برای ۲FA، کد یک‌بارمصرف پشتیبان (Backup Codes) برای زمانی که کاربر به اپ احراز هویتش دسترسی ندارد، و مجوزهای دانه‌ریزتر برای بخش‌های دیگر پنل (محصولات، سفارش‌ها و…) — این‌ها می‌توانند در دوری بعدی به همین زیرساخت (`requireStaffPermission` + `STAFF_ALLOWED`) اضافه شوند.

**تست‌نشده (نیازمند دیتابیس و اجرای واقعی):**
1. اجرای `npx prisma migrate dev`.
2. ساخت یک حساب کارمند با دسترسی SUPPORT از `/admin/staff`، ورود با آن، و بررسی این‌که فقط `/admin/support`، `/admin/contact-messages` و `/admin/security` در دسترسند و بقیه‌ی مسیرهای `/admin/*` او را به صفحه‌ی ورود برمی‌گردانند.
3. راه‌اندازی واقعی ۲FA با یک اپ احراز هویت واقعی (مثلاً Google Authenticator)، تأیید کد، خروج، و ورود دوباره برای دیدن مرحله‌ی دوم؛ همچنین تست وارد کردن کد اشتباه/منقضی.
4. ساخت یک قانون اتوماسیون برای هر سه رویداد و بررسی این‌که با وقوع واقعی رویداد (تحویل سفارش، ثبت تیکت، ارسال فرم تماس)، هشدار/امتیاز واقعاً ساخته می‌شود — و اجرای دوباره‌ی رویداد `ORDER_DELIVERED` پاداش را دوبار نمی‌دهد.

### ۱۳.۱۹ شروع فاز ۱۰ — سخت‌سازی امنیتی، عملکرد و پایداری

**محدودسازی نرخ ورود (Brute-force protection):** قبل از این دور، صفحه‌ی ورود مشتری و ورود پنل مدیریت **هیچ محدودیتی** روی تعداد تلاش‌های ناموفق نداشتند — یعنی یک مهاجم (یا یک لیست پسورد لو‌رفته) می‌توانست بدون هیچ مانعی رمزهای مختلف را روی هر حسابی (از‌جمله حساب ادمین) امتحان کند. این یک شکاف امنیتی واقعی بود، نه یک ویژگی جدید تزئینی. مدل جدید `LoginAttempt` + `lib/loginRateLimit.ts` دقیقاً همان الگوی `TrackLookupAttempt` موجود (محدودیت تلاش پیگیری سفارش) را برای ورود هم پیاده کرده‌اند: حداکثر ۱۰ تلاش ناموفق در هر ۱۵ دقیقه به ازای هر ایمیل؛ بررسی محدودیت **قبل از** هر بررسی رمز/کد ۲FA انجام می‌شود. کد نادرست ۲FA هم یک تلاش ناموفق محسوب می‌شود؛ درخواستِ اول بدون کد (که باعث نمایش فیلد کد می‌شود) محسوب نمی‌شود.

**هدرهای امنیتی HTTP:** `next.config.mjs` حالا `X-Content-Type-Options: nosniff`، `X-Frame-Options: DENY` (چون این سایت هیچ نیاز واقعی به قرارگرفتن داخل iframe سایت دیگری ندارد)، `Referrer-Policy: strict-origin-when-cross-origin`، و `Permissions-Policy` (غیرفعال‌کردن دوربین/میکروفون/موقعیت مکانی، که این سایت هرگز از آن‌ها استفاده نمی‌کند) را برای همه‌ی مسیرها اضافه می‌کند.

**به‌روزرسانی (دور بعدی): Content-Security-Policy واقعاً اضافه شد.** `next.config.mjs` اکنون یک هدر `Content-Security-Policy` واقعی برمی‌گرداند که از یک بازبینی واقعی کد این پروژه ساخته شده (نه یک الگوی کپی‌شده): `script-src`/`style-src` به‌ناچار `'unsafe-inline'` دارند چون این پروژه واقعاً از دو `<script>` درون‌خطی دستی (JSON-LD صفحه محصول، و اسکریپت جلوگیری از پرش حالت تاریک در `ThemeScript.tsx`) و همچنین از `style={{...}}` درون‌خطی React در سراسر رابط کاربری استفاده می‌کند؛ `img-src` هر میزبان `https:` را مجاز می‌کند چون `images.remotePatterns` در همین فایل هم همین‌طور است (ادمین می‌تواند لینک تصویر هر محصول را از هر آدرسی وارد کند)؛ `connect-src` فقط `'self'` است چون تماس با درگاه زرین‌پال کاملاً سمت سرور (Node) انجام می‌شود و مرورگر فقط یک Navigation کامل (نه fetch) به صفحه‌ی خودِ زرین‌پال انجام می‌دهد. **⚠️ صادقانه اعلام می‌شود:** این Sandbox امکان اجرای `next build`/`next dev` و بارگذاری واقعی سایت در مرورگر را ندارد، پس این CSP از روی خواندن کامل کد استدلال شده ولی با کلیک واقعی تست نشده است. **قبل از تکیه‌کردن روی آن در Production:** سایت را لوکال با `npm run build && npm start` اجرا کنید، DevTools Console مرورگر را باز نگه دارید، تمام صفحات واقعی (خانه، دسته‌بندی، جزئیات محصول، سبد خرید، تسویه‌حساب شامل آپلود رسید کارت‌به‌کارت و مسیر بازگشت از زرین‌پال، صفحات حساب کاربری، و کل پنل مدیریت شامل آپلود تصویر محصول) را کلیک کنید، و مطمئن شوید هیچ خطای «Refused to ... because it violates the following Content Security Policy directive» ظاهر نمی‌شود. اگر خطایی دیدید، دقیقاً همان Directive را که نام برده شده کمی بازتر کنید (مثلاً افزودن یک میزبان مشخص به `img-src`).

**ایندکس عملکردی جدید:** `Order.createdAt` — چون `/admin/orders` و صفحه‌ی گزارش‌های مالی هر دو سفارش‌ها را بر اساس تاریخ مرتب/فیلتر می‌کنند و این یکی از رایج‌ترین الگوهای کوئری بدون ایندکس پشتیبان بود.

**تست بار (Load Testing):** انجام نشد — این Sandbox نمی‌تواند یک نمونه‌ی واقعی از این پروژه را روی یک دیتابیس PostgreSQL واقعی اجرا کند تا زیر بار قرار بگیرد؛ هر عددی که بدون اجرای واقعی گزارش می‌شد ساختگی بود. **دستور پیشنهادی برای اجرای واقعی روی سرور واقعی:**
```
npx autocannon -c 50 -d 30 https://your-domain.com/
npx autocannon -c 20 -d 30 https://your-domain.com/api/checkout   # با احتیاط: سفارش واقعی می‌سازد، فقط روی محیط آزمایشی
```

**پشتیبان‌گیری/بازیابی:** اسکریپت‌های `scripts/backup.sh`/`scripts/restore.sh` از قبل موجود بودند (دور قبلی)؛ در این دور فقط صحت نحوی (Syntax) هر دو با `bash -n` دوباره تأیید شد. اجرای واقعی آن‌ها همچنان نیازمند یک دیتابیس PostgreSQL واقعی و `pg_dump`/`pg_restore` است — طبق همان محدودیت همیشگی این Sandbox.

**تست‌نشده (نیازمند دیتابیس و اجرای واقعی):**
1. اجرای `npx prisma migrate dev` برای مدل جدید `LoginAttempt`.
2. تلاش ۱۰+ بار ورود با رمز اشتباه روی یک حساب و بررسی پیام محدودیت.
3. بررسی واقعی هدرهای HTTP پاسخ با `curl -I` روی چند صفحه.
4. یک اجرای کامل `./scripts/backup.sh` و سپس `./scripts/restore.sh` روی یک دیتابیس آزمایشی (نه Production).

### ۱۳.۲۰ تکمیل موارد باقی‌مانده فازهای ۱ تا ۱۰ (این دور)

این دور، آخرین موارد باقی‌مانده‌ی هر فاز را طبق پرامپت اصلی، یکی‌یکی و به‌ترتیب تکمیل کرد — بدون تغییر هیچ ویژگی قبلاً ساخته‌شده. فهرست کامل:

**فاز ۱ — انتخابگر سریع گوشی در صفحه اصلی:** یک ویجت «برند + مدل گوشی خود را انتخاب کنید» در هرو صفحه اصلی (`components/HeroPhonePicker.tsx`) که مستقیماً به `/search?model=...` با همان منطق فیلتر سازگاری موجود وصل است — چیز جدیدی اختراع نشده، فقط یک مسیر میان‌بر واقعی به فیلتر موجود.

**فاز ۲ — امتیاز محصول در کارت‌ها + پرسش و پاسخ محصول:** `Product.avgRating`/`reviewCount` به‌صورت Cache شده (نه محاسبه‌ی زنده روی هر لیست) در همان تراکنش ثبت/ویرایش/حذف نظر بازمحاسبه می‌شود (`recomputeProductRating` در `lib/actions/reviews.ts`) و در کارت محصول در همه‌جا (صفحه اصلی، دسته‌بندی، جستجو، محصولات مرتبط، علاقه‌مندی‌ها) نمایش داده می‌شود — تا وقتی نظر واقعی‌ای ثبت نشده، `avgRating` برابر `null` می‌ماند (نه صفر). یک بخش کاملاً جدید «پرسش از فروشنده» زیر هر محصول اضافه شد (`ProductQuestion` model، `lib/actions/questions.ts`، `components/QASection.tsx`) که کاملاً از نظرات جداست، ورود لازم دارد، و پاسخ‌دهی در `/admin/questions` زیر همان مجوز کارمندیِ SUPPORT قرار گرفته (دقیقاً مثل تیکت و پیام تماس).

**جستجوی فازی/تحمل غلط تایپی:** وقتی جستجوی دقیق نتیجه‌ای ندهد، `lib/products.ts`'s `fuzzyProductSearch` با افزونه‌ی PostgreSQL به نام `pg_trgm` و تابع `similarity()` امتحان می‌شود. **این افزونه به‌صورت پیش‌فرض روی هیچ دیتابیس Postgres نصب نیست** — قبل از استفاده‌ی واقعی باید یک‌بار در دیتابیس اجرا شود:
```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```
اگر این دستور اجرا نشود، کد در `try/catch` می‌افتد و به‌سادگی نتیجه‌ی فازی خالی برمی‌گرداند (نه خطا) — یعنی نبود افزونه هرگز سایت را نمی‌شکند، فقط جستجوی تحمل‌به‌غلط‌تایپی را غیرفعال نگه می‌دارد.

**فاز ۳ — پله‌های تخفیف حجمی عمده‌فروشی + پنل همکاری:** یک مدل جدید `WholesaleTier` (آستانه‌ی تعداد → درصد تخفیف اضافه) که فقط در لحظه‌ی نهایی محاسبه‌ی قیمت در `/api/checkout` روی قیمت عمده اعمال می‌شود (`applyWholesaleTier` در `lib/wholesalePricing.ts`) — هرگز جای دیگری. مدیریت پله‌ها در `/admin/wholesale-tiers`. یک صفحه‌ی اختصاصی `/partner-dashboard` برای شریک تأییدشده اضافه شد که سفارش‌های واقعی خودش (که همین حالا با قیمت عمده ثبت شده‌اند) و پله‌های فعال را نشان می‌دهد — نه یک سیستم سفارش‌دهی موازی.

**فاز ۵ — استفاده واقعی از امتیاز باشگاه مشتریان و پرداخت جزئی از کیف پول در تسویه‌حساب:** این بخش قبلاً فقط زیرساخت (شِما + توابع خالص محاسباتی) داشت؛ در این دور کاملاً به `/api/checkout` وصل شد:
- مشتری می‌تواند بخشی از سفارش را با امتیاز باشگاه مشتریان تخفیف بزند (نرخ تبدیل: هر امتیاز = ۱٬۰۰۰ تومان، حداکثر تا ۵۰٪ کل سفارش — `lib/loyalty.ts`) و/یا بخشی را از کیف پول بپردازد، حتی وقتی روش پرداخت اصلی زرین‌پال یا کارت‌به‌کارت است.
- همه‌چیز روی سرور با claim اتمیک (`updateMany` + شرط `gte`) دوباره چک و از موجودی واقعی کسر می‌شود — هیچ عددی از کلاینت مستقیم اعتماد نمی‌شود.
- اگر مجموع تخفیف امتیاز + کیف پول کل سفارش را پوشش دهد، سفارش همان لحظه `PAID` می‌شود (بدون نیاز به درگاه/کارت‌به‌کارت)، در غیر این صورت فقط باقیمانده (`remainingDue`) به درگاه زرین‌پال یا صفحه‌ی کارت‌به‌کارت فرستاده می‌شود — صفحه‌ی کارت‌به‌کارت (`/checkout/card-transfer/[orderId]`) حالا `order.total - order.walletAmountUsed` را نشان می‌دهد، نه کل مبلغ سفارش.
- فیلدهای جدید `Order.loyaltyPointsUsed`/`loyaltyDiscount`/`walletAmountUsed` در صفحه‌ی جزئیات سفارش (هم پنل ادمین، هم حساب کاربری) نمایش داده می‌شوند — چیزی مخفی نمی‌ماند.
- ⚠️ نکته‌ی امنیتی مهم که همین‌جا هم اصلاح شد: چون مبلغ واقعی درخواستی از زرین‌پال حالا ممکن است کمتر از `order.total` باشد (به‌خاطر پوشش جزئی کیف پول)، مرحله‌ی Verify در `/api/payment/callback` هم به‌روزرسانی شد تا با `order.total - order.walletAmountUsed` تطبیق دهد، نه با `order.total` خام — وگرنه Verify همیشه با مبلغ اشتباه انجام می‌شد.

**فاز ۶ — هشدار موجودی کم (بدون ایمیل/پیامک) + گزارش سود ناخالص + تنظیمات سئو:**
- رویداد جدید `LOW_STOCK` به موتور اتوماسیون بدون‌کد اضافه شد — دقیقاً در لحظه‌ی واقعیِ کسر موجودی در تسویه‌حساب بررسی می‌شود (نه یک Cron جداگانه‌ی شبیه‌سازی‌شده) و فقط وقتی موجودی از بالای آستانه به زیر آن **عبور می‌کند** (نه هر بار که از قبل پایین بوده) اجرا می‌شود، تا هشدار تکراری برای هر فروش ساخته نشود. آستانه از یک تنظیم واقعی (`SiteSettings.lowStockThreshold`، قابل ویرایش در `/admin/settings`) خوانده می‌شود.
- گزارش «سود ناخالص» به `/admin/reports` اضافه شد: درآمد واقعی منهای قیمت تمام‌شده‌ی *فعلی* محصولات (از فیلد از‌قبل‌موجود `Product.costPrice`) روی همه‌ی سفارش‌های واقعاً پرداخت‌شده. **محدودیت صادقانه:** چون قیمت تمام‌شده در لحظه‌ی فروش ذخیره/تاریخچه‌دار نمی‌شود، این عدد از قیمت تمام‌شده‌ی امروز محصول محاسبه می‌شود، نه لحظه‌ی فروش؛ و برای اقلامی که هرگز `costPrice` برایشان ثبت نشده، هزینه‌شان صفر لحاظ می‌شود و همین موضوع صریحاً زیر گزارش به مدیر گفته می‌شود (نه یک عدد نهایی قطعی).
- مدل جدید `SiteSettings` (Singleton، مثل تنظیمات کارت بانکی) برای عنوان/توضیحات سئو، کلمات کلیدی متا، و لینک شبکه‌های اجتماعی (اینستاگرام/تلگرام/واتس‌اپ) — `app/layout.tsx` حالا این مقادیر را در Metadata واقعی صفحات استفاده می‌کند (با بازگشت به مقدار پیش‌فرض قبلی وقتی خالی باشند) و فوتر فقط لینک‌هایی را نشان می‌دهد که واقعاً پر شده باشند — هیچ لینک نمایشی/جعلی نیست.

**فاز ۹ — کدهای پشتیبان یک‌بارمصرف ۲FA:** برای وقتی که کاربر به اپلیکیشن احراز هویتش دسترسی ندارد. هنگام فعال‌سازی اولیه‌ی ۲FA، ۸ کد یک‌بارمصرف تولید و **فقط همان یک لحظه** به‌صورت متن ساده نشان داده می‌شود (`lib/backupCodes.ts`)؛ از آن به بعد فقط هش Bcrypt هرکدام ذخیره می‌شود (دقیقاً مثل رمز عبور). در فرم ورود پنل مدیریت، به‌جای کد ۶ رقمی می‌توان یکی از این کدها را وارد کرد؛ کد مصرف‌شده بلافاصله از لیست حذف می‌شود (دیگر هرگز قابل استفاده نیست). یک دکمه‌ی «ساخت کدهای پشتیبان جدید» (نیازمند رمز عبور) هم در `/admin/security` اضافه شد.

**فاز ۱۰ — تکمیل CSP واقعی:** به بالا (۱۳.۱۹) نگاه کنید — دیگر «عمداً اضافه‌نشده» نیست.

**آنچه از قصد در همین دور خارج از محدوده ماند (و چرا):**
- ارسال ایمیل/پیامک برای هشدار موجودی کم، یا هر اکشن اتوماسیون دیگر — هیچ سرویس ایمیل/پیامکی در این پروژه متصل/تست‌شده نیست؛ افزودن یک اکشن که بی‌صدا شکست می‌خورد بدتر از نداشتنش است.
- اتصال زنده به API شرکت‌های پستی — نیازمند قرارداد/کلید API واقعی یک شرکت مشخص است.
- Page Builder بصری تمام‌عیار (Drag & Drop) — طبق تصمیم صریح قبلی، فاز ۷ در همان محدوده‌ی پایه (بلوک‌های آماده) باقی ماند.
- تست بار واقعی (Load Testing) — دستور آماده در بالا (۱۳.۱۹) هست؛ اجرای واقعی‌اش نیازمند یک سرور واقعی Deploy‌شده است که این Sandbox آن را ندارد.

**تست‌نشده در این بخش (نیازمند دیتابیس/مرورگر واقعی):**
1. `npx prisma migrate dev` برای مدل‌های/فیلدهای جدید: `ProductQuestion`، `WholesaleTier`، `SiteSettings`، `AutomationTrigger.LOW_STOCK`، `Order.loyaltyPointsUsed`/`loyaltyDiscount`/`walletAmountUsed`، `User.twoFactorBackupCodes`.
2. `CREATE EXTENSION IF NOT EXISTS pg_trgm;` روی دیتابیس Production (برای جستجوی فازی).
3. یک خرید کامل با ترکیب امتیاز + کیف پول جزئی + زرین‌پال، و بررسی این‌که مبلغ واقعاً درخواستی از درگاه با مبلغ باقیمانده یکی است.
4. یک خرید که موجودی محصولی را از بالای آستانه به زیر آن ببرد و بررسی ثبت هشدار در `/admin/alerts` (با یک AutomationRule فعال روی `LOW_STOCK`).
5. فعال‌سازی ۲FA، مشاهده‌ی ۸ کد پشتیبان، خروج، و ورود مجدد با یکی از همان کدها به‌جای کد اپلیکیشن — و بررسی این‌که همان کد بار دوم دیگر کار نکند.
6. بررسی کامل CSP طبق چک‌لیست بخش ۱۳.۱۹ (کلیک روی تمام صفحات با DevTools Console باز).

### ۱۳.۲۱ رفع باگ واقعی — ریسپانسیو نبودن پنل مدیریت روی موبایل

کاربر روی سرور واقعی گزارش داد که روی موبایل به «بعضی دکمه‌ها و امکانات پنل مدیریت» دسترسی ندارد (یک مشکل جداگانه — کار نکردن دکمه‌های دسکتاپ — توسط خود کاربر به قطعی اینترنت نسبت داده شد، نیازی به تغییر کد نداشت).

بررسی کد **دو باگ واقعی و مجزا** پیدا کرد:

1. **هیچ منویی روی موبایل وجود نداشت.** `app/admin/(protected)/layout.tsx` کل سایدبار را با `hidden md:flex` فقط در دسکتاپ نشان می‌داد، و بخش هدر موبایل هیچ جایگزینی برایش نداشت. **رفع شد:** `components/admin/AdminMobileNav.tsx` — منوی همبرگری با کشو، که همان `visibleNav`/مجوزهای RBAC محاسبه‌شده در سرور را (به‌عنوان prop) نشان می‌دهد؛ هیچ منطق دسترسی جداگانه‌ای تکرار نشده.
2. **دکمه‌های ویرایش/حذف در جدول‌ها روی موبایل پنهان می‌شدند.** هر ۱۵ جدول پنل مدیریت داخل یک `div` با `overflow-hidden` بودند که روی عرض کم، به‌جای اسکرول افقی، ستون‌های سمت چپ (شامل ستون «عملیات») را کلیپ و پنهان می‌کرد. **رفع شد:** افزودن یک لایه‌ی `overflow-x-auto` داخل هر ۱۵ فایل (محصولات، سفارش‌ها، کاربران، تخفیف‌ها، برندها/مدل‌ها/رنگ‌ها، تیکت‌ها، پیام‌ها، صفحات محتوایی، پله‌های عمده، هشدارها، اتوماسیون، دسته‌بندی‌ها، قوانین قیمت‌گذاری، متغیرهای محصول).

بررسی صحت: توازن نحوی روی هر ۱۷ فایل تغییریافته ✅، و یک اجرای `tsc --noEmit` مجزا که فقط همان کدهای نویز محیطی همیشگی را نشان داد. جزئیات کامل در `TEST_REPORT.md`.

**تست‌نشده (نیازمند مرورگر موبایل واقعی):** باز/بسته‌کردن منوی همبرگری و اسکرول‌کردن افقی یک جدول تا دیدن دکمه‌های عملیات، روی یک گوشی واقعی.
